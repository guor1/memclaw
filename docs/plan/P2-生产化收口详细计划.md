## 0. P2 目标与原则

**目标**：让 oc 能**长期挂着跑、对外发布**，从"功能完整的原型"升级为"生产可用的系统"。

**核心差距**：
- **可用性瓶颈**：读写未分离 → 慢查询阻塞全体会话；写线程 panic 无自愈 → 数据层瘫痪需重启
- **内存泄漏**：IdempotencyCache / SessionActor 无淘汰 → 长期运行内存单调增长
- **工程化缺口**：无 CI、配置热更未接线、unix socket 未在 Linux 实跑

**指导原则**：
1. **可用性优先**：读写分离、写线程自愈先做（影响 7×24 运行）
2. **分阶段验收**：每项独立可演示、可回滚
3. **真机验证**：P2 各项完成后，挂载真机跑满 7 天，观察内存/日志/响应时间

## P2-1 读写分离 🔴 ✅ 已完成（2026-09-06）

> **落地**：新增 [reader.rs](../../crates/oc-store/src/reader.rs)——`Vec<Connection>` +
> `Mutex` 的小池（非 r2d2），每次读在 `spawn_blocking` 里跑同步 rusqlite。池空时开
> 短连接、归还时池满则关，所以 `MAX_IDLE` 是**常驻上限**而非并发上限，突发并发不排队。
> `Store` 门面加同名读方法做分流（`load_transcript` / `search_candidates` /
> `dream_candidates` / `memory_by_pref_key` / `session_list` / `cron_list` / `intent_list`）。
>
> **读连接置 `PRAGMA query_only=ON`**：不以只读模式打开（WAL 的 `-shm` 在纯只读连接上
> 有开不出来的坑），而是让 SQLite 自己拒绝写语句——「唯一可写连接只有写线程那条」
> 因此是数据库强制的，不是「约定这里只写 SELECT」。
>
> **内存库例外**：`reader=None` 时读回落写线程。`:memory:` 每条连接一个**独立库**，
> 共享它要 `cache=shared` URI，那会关掉 WAL 并引入 `busy_timeout` 管不着的
> `SQLITE_LOCKED_SHAREDCACHE`。测试用内存库图的是快和干净，不值得为此换一套并发语义。
> 两条路径共用同一个 `ops::*` 函数，回落只是少了并行、不是另一套实现。
> 生产路径 `open_path` 始终有池。
>
> **连带修正**：`oc debug` 的 `store_writer_alive` 原本拿 `session_list()` 当探针；
> 读一挪走那条命令就不再经过写线程了——写线程死了它也会返回 true。改用 `writer_ping()`。

### 背景
**现状**（与设计 §3.1 矛盾）：
```rust
// 设计承诺：读走短连接或小连接池 + spawn_blocking
// 实际：读写共用单写线程，慢查询阻塞全体会话
```

**影响**：
- 大型记忆检索（`memory.text LIKE '%term%'` 全表扫描）会拖累主会话响应
- Lane1 排名 / standing intent 预筛若慢，会让每条消息都卡顿

### 改动方案

#### 1.1 读连接池（简单版）
```rust
// oc-store/src/lib.rs
pub struct ReadPool {
    conns: Arc<Mutex<Vec<Connection>>>,  // 小池子，2-4 个连接
    db_path: PathBuf,
}

impl ReadPool {
    pub fn get(&self) -> StoreResult<PooledConn> {
        let mut conns = self.conns.lock().unwrap();
        conns.pop()
            .map(|c| PooledConn { conn: Some(c), pool: self.conns.clone() })
            .ok_or_else(|| {
                // 池空，临时开短连接
                Connection::open(&self.db_path).map(|c| PooledConn::shortlived(c))
            })?
    }
}

struct PooledConn {
    conn: Option<Connection>,
    pool: Arc<Mutex<Vec<Connection>>>,
}

impl Drop for PooledConn {
    fn drop(&mut self) {
        if let Some(c) = self.conn.take() {
            self.pool.lock().unwrap().push(c);  // 还回池
        }
    }
}
```

#### 1.2 读操作改走 spawn_blocking
```rust
// Store trait 实现
async fn rank_search(&self, q: RankQuery) -> StoreResult<Vec<MemHit>> {
    let pool = self.read_pool.clone();
    let q = q.clone();
    tokio::task::spawn_blocking(move || {
        let conn = pool.get()?;
        ops::rank_search_candidates(&conn, &q)  // 同步 rusqlite 调用
    }).await?
}
```

#### 1.3 写保持单写线程不变
- WriterActor 继续持有唯一可写连接
- WAL 模式下读不阻塞写（SQLite 保证）

### 验收
- [x] 写队列积压 3000 条时读仍立即返回（`read_is_not_queued_behind_pending_writes`）。
      **构造方式换了**：原计划的「插 10 万行 + LIKE 扫描」依赖机器性能、阈值难定；
      改用「灌满写队列再计时一次读」，判据是读耗时 vs 队列排空耗时的**比值**，
      与机器速度无关。已验证它抓得住回归——把分流改回写线程当场变红
      （读 337ms vs 排空 346ms）。
- [x] 写线程健康指标独立于读（`writer_ping()`，见上方「连带修正」）
- [x] 单测：并发 10 个读 + 1 个写，所有操作都成功（`concurrent_reads_and_write_all_succeed`）

回归见 [read_write_split.rs](../../crates/oc-store/tests/read_write_split.rs)
（真文件库——内存库无池，拿它跑这几条会永远失败，文件头有注明）。

## P2-2 写线程 panic 自愈 🔴 ✅ 已完成（2026-09-06）

> **落地**：写线程内挂 `HealthGuard`（RAII，drop 时翻 `alive` 位）。用 RAII 而非在
> `run_loop` 末尾赋值——panic 展开**不会**走到函数末尾，而 panic 恰恰是本机制最想
> 覆盖的情形。新增 `StoreError::WriterDead`（单列变体而非塞进 `Migration(String)`：
> 调用方需要能区分「这次写失败了」与「写侧整体不可用」）、`Writer::is_alive()`
> （一次原子读，可在每个写操作前调）、`Writer::ping()`（no-op 命令，答「队列还在
> 推进吗」——长事务卡住时线程活着但不动，`is_alive` 单独答不了这一问）。
>
> **降级面**：写侧死后读仍可用（走 P2-1 的独立连接池），由
> `reads_survive_dead_writer` 钉住。这是读写分离顺带买到的——**写侧瘫痪不再等于
> 存储层整体瘫痪**。
>
> **顺带**：22 个转发方法逐字重复同样四行，改一次错误语义要改 22 处（本次正是如此），
> 提成 `writer_call!` 宏。
>
> **未做**：`Event::SystemWarning` 推送给 client（原方案 2.3「可选」项）。要加 proto
> 事件 + TUI 渲染，跨三个 crate；当前写线程死后的可见性是 `oc debug` 的
> `store_writer_alive=false` + 日志 + 写操作返回明确错误。真机遇到过再补。
> 也**不做热重启**——写线程 panic 说明有 bug 或环境异常（DB 损坏、磁盘满），
> 盲目重启可能循环崩溃。

### 背景
**现状**：
```rust
// WriterActor 的 JoinHandle 被丢弃
tokio::spawn(async move { writer_loop(rx).await });  // ← 返回的 handle 未持有
// panic 后无人监控 → 存储层瘫痪 → 进程看似正常但无法写入
```

**风险**：写线程 panic（DB 损坏、磁盘满、迁移 bug）→ 进程僵死、用户无感知

### 改动方案

#### 2.1 监控 JoinHandle
```rust
pub struct Store {
    writer_tx: mpsc::Sender<WriteCmd>,
    writer_handle: Arc<Mutex<Option<JoinHandle<()>>>>,  // ← 持有 handle
    health: Arc<AtomicBool>,  // 快速健康检查（避免每次锁 Mutex）
}

pub async fn start_store(db_path: &Path) -> StoreResult<Store> {
    let (tx, rx) = mpsc::channel(128);
    let health = Arc::new(AtomicBool::new(true));
    let health_clone = health.clone();
    
    let handle = tokio::spawn(async move {
        if let Err(e) = writer_loop(rx).await {
            error!("Writer thread failed: {}", e);
        }
        health_clone.store(false, Ordering::SeqCst);  // 标记不健康
    });
    
    Ok(Store {
        writer_tx: tx,
        writer_handle: Arc::new(Mutex::new(Some(handle))),
        health,
    })
}
```

#### 2.2 健康检查 + 降级模式
```rust
impl Store {
    async fn check_health(&self) -> StoreResult<()> {
        if !self.health.load(Ordering::SeqCst) {
            return Err(StoreError::WriterDead);

        let (tx, rx) = oneshot::channel();

            .map_err(|_| StoreError::WriterDead)?;
        rx.await.map_err(|_| StoreError::WriterDead)?;
        
        Ok(())
    }
    
    async fn upsert_memory(&self, m: NewMemory) -> StoreResult<MemoryId> {
        self.check_health().await?;  // ← 每个写操作先检查
        // 原有逻辑...
    }
}
```

## P2-3 IdempotencyCache + SessionActor 淘汰 🟠 ✅ 已完成（2026-09-06，真机 48h 待观察）

> **落地**：幂等条目加时间戳（[state.rs](../../crates/oc-server/src/state.rs)），`get` 时
> 判 TTL 并顺手删过期项；但**只靠 get 删不够**——写进去就再没人查的冷键永远收不掉，
> 故另有定期清扫。会话侧新增 `SessionCmd::EvictIfIdle` 探针 +
> `SessionRegistry::evict_idle`。
>
> **判定权在 actor，不在 registry**：registry 能看到的只有「上次 `get_or_spawn` 的
> 时刻」，那是个坏代理——一条连接握着句柄连续跑几小时不再查 registry，按那个时刻算
> 会把正忙的会话判成空闲。「有无活跃 run / 有无排队轮 / 上次处理命令距今多久」只有
> actor 自己知道。
>
> **actor 先关接收端再回执**：于是 registry 收到 `true` 时 `Sender::is_closed()` 必然
> 已为真，`remove_if` 的判据是确定的，不靠时序赌。
>
> **原方案的两处修正**：
> 1. 「actor 的 handle drop 会自动 abort 任务」——在本仓**不成立**。actor 自己持有
>    `self_tx`（用来投 `Finished`），registry 单方面丢条目不会让 `rx.recv()` 返回
>    `None`，任务会永久挂在那儿。必须让 actor 显式退出，这也是探针要有回执的原因。
> 2. 注册表里留一条**死句柄**会让该会话**永久**不可用：`submit()` 恒返回 `None`，
>    dispatch 把它报成「队列已满」，而队列其实空着、只是没人收命令。故
>    `get_or_spawn` 见死句柄即换新 actor，dispatch 在这条路径上重试一次。
>
> **比原方案多做的**：原方案只淘汰 actor。但 `diag`（诊断格位）与 `usage`（每会话
> 最近用量）**同为 `SessionId` 键、同样无界**——只收 actor 等于把增长从一处挪到另
> 两处，「内存单调增长」只治了三分之一。三者统一由 `ServerState::gc_tick` 一起收。
>
> **GC 挂在既有 60s 心跳上**，而非原方案的两个独立定时任务（10min/30min）。心跳已有
> 关停接线，两项活儿又都是「扫一遍、都很便宜」（幂等表全扫是单用户量级的微秒级；
> 探针是一次 `try_send` + oneshot）。少两个 task、少两处生命周期管理。
>
> **顺带**：`DiagnosticsSnapshot` 加 `idem_entries` 计数 + `oc debug` 显示。没有它，
> 下面「跑 48h 观察内存稳定」这条验收根本没法看——会话行数肉眼可数，幂等键数此前
> 无从得知。
>
> **未做**：TTL / 空闲阈值仍是常量（`IDEM_TTL` 1h、`SESSION_IDLE_TIMEOUT` 24h），
> 未进 config。两者都不是用户该调的旋钮，且配置热更的去向本身还悬着（P2-5）。

### 背景
**现状**：
```rust
// IdempotencyCache: DashMap<IdemKey, CachedRes>，无 TTL/LRU
// SessionActor: DashMap<SessionId, ActorHandle>，永不退出
// → 长期运行内存单调增长
```

**影响**：
- 大量随机 session_id 会累积空闲 actor
- 幂等键 TTL 过长会占内存（虽单用户量不大，但影响认知）

### 改动方案

#### 3.1 IdempotencyCache TTL
```rust
struct CachedRes {
    res: MethodOk,
    cached_at: Instant,
}

impl IdempotencyCache {
    pub fn get(&self, key: &IdemKey) -> Option<MethodOk> {
        self.map.get(key).and_then(|entry| {
            if entry.cached_at.elapsed() > Duration::from_secs(3600) {  // 1h TTL
                self.map.remove(key);  // 过期删除
                None
            } else {
                Some(entry.res.clone())
            }
        })
    }
    
    // 可选：后台任务定期扫描清理（避免 get 时才删，导致冷键永久占内存）
    pub fn start_gc_task(&self) {
        let map = self.map.clone();
        tokio::spawn(async move {
            loop {
                tokio::time::sleep(Duration::from_secs(600)).await;  // 每 10 分钟
                map.retain(|_, v| v.cached_at.elapsed() < Duration::from_secs(3600));
            }
        });
    }
}
```

#### 3.2 SessionActor 空闲淘汰
```rust
struct SessionEntry {
    handle: ActorHandle,
    last_activity: Arc<AtomicU64>,  // unix millis
}

impl SessionRegistry {
    pub fn start_idle_gc(&self) {
        let registry = self.map.clone();
        tokio::spawn(async move {
            loop {
                tokio::time::sleep(Duration::from_secs(1800)).await;  // 每 30 分钟
                let now = now_millis();
                let idle_threshold = 24 * 3600 * 1000;  // 24h 无活动
                
                registry.retain(|id, entry| {
                    let last = entry.last_activity.load(Ordering::Relaxed);
                    if now - last > idle_threshold {
                        info!("Evicting idle session: {}", id);
                        false  // 淘汰（actor 的 handle drop 会自动 abort 任务）
                    } else {
                        true
                    }
                });
            }
        });
    }
}
```

**单用户优化**：主会话（`session_id = "main"`）**永不淘汰**，只淘汰隔离子会话（cron/dreaming/Lane2）

### 验收
- [x] 单测：幂等键过 TTL 后再查返回 `None`（`idem_entry_expires_after_ttl`，
      `start_paused` + `time::advance` 推时钟，不真等一小时）
- [x] 单测：**冷键**也会被清扫收掉（`gc_sweeps_cold_expired_idem_keys`）。原验收没这条，
      但只在 `get` 时删会漏掉「写进去就再没人查」的键——那恰恰是最会攒的一类
- [x] 单测：闲置子会话被淘汰、`main` 不淘汰（`idle_subsession_is_evicted_main_is_kept`）
- [x] 单测：正忙的不淘汰（`busy_session_is_not_evicted`）、近期活动过的不淘汰
      （`recent_activity_blocks_eviction`）
- [x] 单测：心跳自己的健康扫描不算「活动」（`health_scan_does_not_count_as_activity`）
- [x] 单测：淘汰连带清掉诊断/用量格位（`eviction_clears_diag_and_usage_slots`）
- [x] 单测：被淘汰的会话下次说话能重建并带回历史
      （`evicted_session_respawns_with_history`——淘汰不丢状态，因为状态在 SQLite）
- [x] 单测：注册表里的死句柄会被换掉（`get_or_spawn_replaces_dead_handle`）
- [ ] 真机：跑 48h，观察内存稳定（不单调增长）← **待做**。观测手段已备好：
      `oc debug` 头行的 `idem` 计数 + 会话行数，两处都不该随时间单调上涨

**测试的时间策略**（踩过坑，记下来）：会话侧**注入短阈值**（`gc_tick_with`）而非推
时钟。推时钟在 actor 路径上不可靠——actor 启动要 `ensure_session`（一次写线程往返），
此间 runtime 无待跑任务 → 暂停时钟**自动推进** → 淘汰探针的 2s 超时先响，
`last_activity` 反而在 `advance` 之后才初始化，于是实现正确也判「刚活动过」。
幂等侧只碰 map、无 actor，推时钟安全。

`health_scan_does_not_count_as_activity` 是唯一熬真实时间的（1.2s）：阈值取 ZERO 时
判定式 `elapsed() < ZERO` 恒为假，改坏实现照样绿（第一版正是如此）；非零阈值就得让
时间真的流过去，而这条又不能推时钟（同上）。

回归见 [gc.rs](../../crates/oc-server/tests/gc.rs)（9 项）。**已验证抓得住回归**：
逐个改坏 6 处实现（HealthScan 计入活动 / 忽略活跃 run / 交出死句柄 / 不清诊断用量格位 /
幂等键永不过期 / main 也淘汰），每个都当场变红。

### 成本
实际约 0.5 天（低于估的 2-3 天：判定权交给 actor 后不需要共享的
`Arc<AtomicU64>`，注入阈值又把「模拟时间流逝」压到只剩两条用例）

## P2-4 memory.text 索引（FTS5 或列索引）🟠 ✅ 已完成（2026-09-10）

> **落地**：新增 [fts.rs](../../crates/oc-store/src/fts.rs)（编码）+ `memory_fts` 虚表
> （[schema.rs](../../crates/oc-store/src/schema.rs)）。**计划书推荐的分词器不能用**：
> `unicode61` 把一整段中文当**一个** token——索引里存着 `用户喜欢简洁的回复`，查
> `简洁` 得零行，中文召回会静默归零；`trigram` 又只对 ≥3 字的词生效，而上层
> `tokenize()` 刻意产 **2-gram**（覆盖中文双字词）。于是**不换分词器、换存进去的东西**：
> 把文本预切成「相邻两字」的词流交给 `unicode61`（它只按空格切开我们给的 token），
> 查询侧用同一函数编码——索引天然是 LIKE 结果的超集，`LIKE` 复核保留在 SQL 里负责
> 最终判定，故**结果集与纯 LIKE 完全一致**，只是不再全表扫。
>
> **表用 contentless**（`content=''`，原文已在 memory.text）＋ `detail=none`（不存词位，
> 所以查不到相邻性——正是留给 LIKE 复核的那部分）+ `contentless_delete=1`
> （contentless 表默认删不掉行，而记忆会被 supersede 替换和删除）。空间代价实测
> 10 万条 = 表的 **28%**，存内容则 200~300%。
>
> **三个踩过坑的坑**：①contentless 表的 INSERT 不认 rowid 冲突，同 rowid 插两次会
> **累积** token，且累积的旧 token 连 DELETE 都清不净（只清最后一次那批）——upsert
> 必须**先删后插**；②contentless 表只能靠 rowid 关联回主表，而 SQLite 只保证
> **声明了** `INTEGER PRIMARY KEY` 的 rowid 在 VACUUM 后不变，故 memory 加了显式
> `no INTEGER PRIMARY KEY` 列（id 改 UNIQUE 保持等价约束）；③候选排序改用 `no DESC`
> 而非 `created_at DESC`——按 created_at 排要把命中行灌进临时 B-tree，实测 80~140ms
> 反而比纯 LIKE 还慢，按 rowid 逆序读才是 1~7ms 的快路径。
>
> **验收实测**（10 万条、每条数百字）：最慢查询 **2.7ms**（全表 LIKE 对照 243ms，
> 差 90 倍），28 个查询形状逐一与纯 LIKE 结果集相同、0 漏召回、0 误召回。
> 可重复的基准在 [memory_fts.rs](../../crates/oc-store/tests/memory_fts.rs) 的
> `search_stays_fast_at_100k_rows`（`#[ignore]`，按需跑）。
>
> **连带**：`oc doctor` 加 [check_shape](../../crates/oc-store/src/lib.rs)——开发阶段
> 改 DDL 不写迁移，旧库的 `user_version` 已经等于目标值、迁移整个 no-op，但表结构是
> 旧的，第一次写记忆才炸 `no such table: memory_fts`。版本号查不出来，查结构才查得出来。

### 背景
**现状**：


**影响**：10 万条记忆时查询 >1s

### 改动方案

#### 方案 A：SQLite FTS5（推荐）

```sql
-- 每次插入 memory 时同步插入 fts 表
```

```rust
// oc-server/src/session.rs
async fn call_model_with_failover(&self, req: ModelRequest) -> Result<Delta, ModelError> {
    let mut tried = vec![];
    loop {
        let provider_id = resolve_alias(&self.catalog, &req.model)?;
        let provider = self.providers.get(&provider_id)?;
        
        match provider.stream_chat(req.clone(), cancel.clone()).await {
            Ok(stream) => return Ok(stream),
            Err(e) if e.is_retryable() => {
                tried.push(provider_id);
                if let Some(fallback) = failover_plan(&self.catalog, &tried, &e) {
                    warn!("Provider {} failed, trying fallback {}", provider_id, fallback);
                    req.model = fallback;  // 切换模型
                    continue;
                } else {
                    return Err(e);  // 无更多 fallback
                }
            }
            Err(e) => return Err(e),  // 非可重试错误，直接失败
        }
    }
}
```

**配置示例**：
```toml
[[models]]
alias = "default"
provider = "anthropic"
model = "claude-sonnet-4-20250514"
failover = ["openai:gpt-4o"]  # 失败时切换

[[models]]
alias = "openai:gpt-4o"
provider = "openai"
model = "gpt-4o"
```
