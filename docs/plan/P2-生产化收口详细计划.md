## 0. P2 目标与原则

**目标**：让 oc 能**长期挂着跑、对外发布**，从"功能完整的原型"升级为"生产可用的系统"。

**核心差距**：
- **可用性瓶颈**：读写未分离 → 慢查询阻塞全体会话；写线程 panic 无自愈 → 数据层瘫痪需重启
- **内存泄漏**：IdempotencyCache / SessionActor 无淘汰 → 长期运行内存单调增长
- **工程化缺口**：无 CI、配置热更未接线、unix socket 未在 Linux 实跑

**指导原则**：
1. **可用性优先**：读写分离、写线程自愈先做（影响 7×24 运行）
2. **分阶段验收**：每项独立可演示、可回滚
3. **真机验证**：P2 各项完成后，挂载真机跑满 7 天，观察内存/日志/响应时间

## P2-1 读写分离 🔴 （高优先级）

### 背景
**现状**（与设计 §3.1 矛盾）：
```rust
// 设计承诺：读走短连接或小连接池 + spawn_blocking
// 实际：读写共用单写线程，慢查询阻塞全体会话
```

**影响**：
- 大型记忆检索（`memory.text LIKE '%term%'` 全表扫描）会拖累主会话响应
- Lane1 排名 / standing intent 预筛若慢，会让每条消息都卡顿

### 改动方案

#### 1.1 读连接池（简单版）
```rust
// oc-store/src/lib.rs
pub struct ReadPool {
    conns: Arc<Mutex<Vec<Connection>>>,  // 小池子，2-4 个连接
    db_path: PathBuf,
}

impl ReadPool {
    pub fn get(&self) -> StoreResult<PooledConn> {
        let mut conns = self.conns.lock().unwrap();
        conns.pop()
            .map(|c| PooledConn { conn: Some(c), pool: self.conns.clone() })
            .ok_or_else(|| {
                // 池空，临时开短连接
                Connection::open(&self.db_path).map(|c| PooledConn::shortlived(c))
            })?
    }
}

struct PooledConn {
    conn: Option<Connection>,
    pool: Arc<Mutex<Vec<Connection>>>,
}

impl Drop for PooledConn {
    fn drop(&mut self) {
        if let Some(c) = self.conn.take() {
            self.pool.lock().unwrap().push(c);  // 还回池
        }
    }
}
```

#### 1.2 读操作改走 spawn_blocking
```rust
// Store trait 实现
async fn rank_search(&self, q: RankQuery) -> StoreResult<Vec<MemHit>> {
    let pool = self.read_pool.clone();
    let q = q.clone();
    tokio::task::spawn_blocking(move || {
        let conn = pool.get()?;
        ops::rank_search_candidates(&conn, &q)  // 同步 rusqlite 调用
    }).await?
}
```

#### 1.3 写保持单写线程不变
- WriterActor 继续持有唯一可写连接
- WAL 模式下读不阻塞写（SQLite 保证）

### 验收
- [ ] 构造慢查询（`memory` 表插 10 万行 + `LIKE '%term%'`），观察主会话仍能秒回
- [ ] `oc debug --watch` 确认读操作不占用写线程（写线程健康指标独立）
- [ ] 单测：并发 10 个读 + 1 个写，所有操作都成功

### 成本
3-5 天（ReadPool 实现 + Store trait 所有读方法改造 + 回归测试）

## P2-2 写线程 panic 自愈 🔴 （高优先级）

### 背景
**现状**：
```rust
// WriterActor 的 JoinHandle 被丢弃
tokio::spawn(async move { writer_loop(rx).await });  // ← 返回的 handle 未持有
// panic 后无人监控 → 存储层瘫痪 → 进程看似正常但无法写入
```

**风险**：写线程 panic（DB 损坏、磁盘满、迁移 bug）→ 进程僵死、用户无感知

### 改动方案

#### 2.1 监控 JoinHandle
```rust
pub struct Store {
    writer_tx: mpsc::Sender<WriteCmd>,
    writer_handle: Arc<Mutex<Option<JoinHandle<()>>>>,  // ← 持有 handle
    health: Arc<AtomicBool>,  // 快速健康检查（避免每次锁 Mutex）
}

pub async fn start_store(db_path: &Path) -> StoreResult<Store> {
    let (tx, rx) = mpsc::channel(128);
    let health = Arc::new(AtomicBool::new(true));
    let health_clone = health.clone();
    
    let handle = tokio::spawn(async move {
        if let Err(e) = writer_loop(rx).await {
            error!("Writer thread failed: {}", e);
        }
        health_clone.store(false, Ordering::SeqCst);  // 标记不健康
    });
    
    Ok(Store {
        writer_tx: tx,
        writer_handle: Arc::new(Mutex::new(Some(handle))),
        health,
    })
}
```

#### 2.2 健康检查 + 降级模式
```rust
impl Store {
    async fn check_health(&self) -> StoreResult<()> {
        if !self.health.load(Ordering::SeqCst) {
            return Err(StoreError::WriterDead);
        }
        
        // 可选：定期 ping（发一个 no-op 命令，确认通道未关闭）
        let (tx, rx) = oneshot::channel();
        self.writer_tx.send(WriteCmd::HealthCheck(tx)).await
            .map_err(|_| StoreError::WriterDead)?;
        rx.await.map_err(|_| StoreError::WriterDead)?;
        
        Ok(())
    }
    
    async fn upsert_memory(&self, m: NewMemory) -> StoreResult<MemoryId> {
        self.check_health().await?;  // ← 每个写操作先检查
        // 原有逻辑...
    }
}
```

#### 2.3 降级策略（可选）
- **只读模式**：写线程死后，拒绝所有写、允许读（靠 ReadPool）
- **用户通知**：发 `Event::SystemWarning` → client 显示"存储层异常，仅只读"
- **不做热修复**：写线程 panic 说明有 bug 或环境异常，盲目重启可能循环崩溃，
  不如明确降级、等人工介入

### 验收
- [ ] 单测：模拟写线程 panic（WriterActor 里主动 `panic!`），Store 后续写操作返回 `WriterDead` 错误
- [ ] 单测：写线程死后，读操作仍可用（ReadPool 独立）
- [ ] 真机：手动 kill 写线程（若可隔离测试），观察日志 + client 收到降级通知

### 成本
1-2 天（健康检查机制 + 降级逻辑 + 回归测试）

## P2-3 IdempotencyCache + SessionActor 淘汰 🟠 （中优先级）

### 背景
**现状**：
```rust
// IdempotencyCache: DashMap<IdemKey, CachedRes>，无 TTL/LRU
// SessionActor: DashMap<SessionId, ActorHandle>，永不退出
// → 长期运行内存单调增长
```

**影响**：
- 大量随机 session_id 会累积空闲 actor
- 幂等键 TTL 过长会占内存（虽单用户量不大，但影响认知）

### 改动方案

#### 3.1 IdempotencyCache TTL
```rust
struct CachedRes {
    res: MethodOk,
    cached_at: Instant,
}

impl IdempotencyCache {
    pub fn get(&self, key: &IdemKey) -> Option<MethodOk> {
        self.map.get(key).and_then(|entry| {
            if entry.cached_at.elapsed() > Duration::from_secs(3600) {  // 1h TTL
                self.map.remove(key);  // 过期删除
                None
            } else {
                Some(entry.res.clone())
            }
        })
    }
    
    // 可选：后台任务定期扫描清理（避免 get 时才删，导致冷键永久占内存）
    pub fn start_gc_task(&self) {
        let map = self.map.clone();
        tokio::spawn(async move {
            loop {
                tokio::time::sleep(Duration::from_secs(600)).await;  // 每 10 分钟
                map.retain(|_, v| v.cached_at.elapsed() < Duration::from_secs(3600));
            }
        });
    }
}
```

#### 3.2 SessionActor 空闲淘汰
```rust
struct SessionEntry {
    handle: ActorHandle,
    last_activity: Arc<AtomicU64>,  // unix millis
}

impl SessionRegistry {
    pub fn start_idle_gc(&self) {
        let registry = self.map.clone();
        tokio::spawn(async move {
            loop {
                tokio::time::sleep(Duration::from_secs(1800)).await;  // 每 30 分钟
                let now = now_millis();
                let idle_threshold = 24 * 3600 * 1000;  // 24h 无活动
                
                registry.retain(|id, entry| {
                    let last = entry.last_activity.load(Ordering::Relaxed);
                    if now - last > idle_threshold {
                        info!("Evicting idle session: {}", id);
                        false  // 淘汰（actor 的 handle drop 会自动 abort 任务）
                    } else {
                        true
                    }
                });
            }
        });
    }
}
```

**单用户优化**：主会话（`session_id = "main"`）**永不淘汰**，只淘汰隔离子会话（cron/dreaming/Lane2）

### 验收
- [ ] 单测：幂等键 1h 后再查返回 `None`（需要 `tokio::time::pause` 模拟时间流逝）
- [ ] 单测：子会话 24h 无活动后被淘汰（registry 不再持有）
- [ ] 真机：跑 48h，观察内存稳定（不单调增长）

### 成本
2-3 天（TTL 逻辑 + GC 任务 + 时间模拟单测 + 真机验证）

## P2-4 memory.text 索引（FTS5 或列索引）🟠 （中优先级）

### 背景
**现状**：
```sql
SELECT * FROM memory WHERE text LIKE '%term%';  -- 全表扫描
```

**影响**：10 万条记忆时查询 >1s

### 改动方案

#### 方案 A：SQLite FTS5（推荐）
```sql
-- 迁移脚本（新版本）
CREATE VIRTUAL TABLE memory_fts USING fts5(memory_id, text, tokenize='porter unicode61');

-- 每次插入 memory 时同步插入 fts 表
INSERT INTO memory_fts(memory_id, text) VALUES(?, ?);

-- 查询改走 FTS
SELECT m.* FROM memory m
JOIN memory_fts fts ON fts.memory_id = m.id
WHERE fts.text MATCH ?  -- FTS 查询（支持布尔运算、短语匹配）
```

**优点**：全文检索能力强、性能好  
**缺点**：FTS 表会占额外空间（约原表 50-100%）

#### 方案 B：keywords 列索引（当前已有 keywords 列）
```sql
CREATE INDEX idx_memory_keywords ON memory(keywords);  -- 若还没建

-- 查询改走 keywords（词法预筛）
SELECT * FROM memory WHERE keywords LIKE '%' || ? || '%';
-- 或改用 json_each + 精确匹配（若 keywords 改存 JSON 数组）
```

**优点**：轻量、复用已有列  
**缺点**：只能词法匹配、不如 FTS 灵活

**推荐**：方案 A（FTS5），keywords 列保留用于预筛（intersection）

### 验收
- [ ] 10 万条记忆，`memory_search` 查询 <100ms（当前 >1s）
- [ ] 迁移脚本前向兼容（老库升级后自动建 FTS 表 + 回填已有数据）

### 成本
2-3 天（迁移脚本 + ops 改造 + 性能基准测试）

## P2-5 配置热更接线或移除 ArcSwap 🟡 （低优先级）

### 背景
**现状**：
```rust

// 但无实际热更逻辑 → 改配置需重启
```

**选择**：要么实现热更，要么改用普通 `Arc` 并在文档明确"需重启"

### 改动方案

#### 方案 A：实现热更（若需要）
```rust
pub fn start_config_watcher(cfg_path: &Path, swap: Arc<ArcSwap<Config>>) {
    let path = cfg_path.to_owned();
    tokio::spawn(async move {
        let mut watcher = notify::recommended_watcher(|event| { /* ... */ })?;
        watcher.watch(&path, RecursiveMode::NonRecursive)?;
        
        loop {
            // 收到文件变更事件
```


**推荐**：方案 B（单用户场景重启成本低，热更收益小）

- [ ] 若选方案 A：修改 `config.toml` 后 5s 内生效（不重启 daemon）
- [ ] 若选方案 B：文档明确 + 改用 `Arc`（clippy 不再建议 ArcSwap）

### 成本

## P2-6 Provider failover 接线 🟡 （低优先级）

### 背景
**现状**：
```rust
// oc-core 已有 failover_plan / resolve_alias（纯函数）
// 但无调用方 → 模型调用失败不会自动切换
```

### 改动方案

```rust
// oc-server/src/session.rs
async fn call_model_with_failover(&self, req: ModelRequest) -> Result<Delta, ModelError> {
    let mut tried = vec![];
    loop {
        let provider_id = resolve_alias(&self.catalog, &req.model)?;
        let provider = self.providers.get(&provider_id)?;
        
        match provider.stream_chat(req.clone(), cancel.clone()).await {
            Ok(stream) => return Ok(stream),
            Err(e) if e.is_retryable() => {
                tried.push(provider_id);
                if let Some(fallback) = failover_plan(&self.catalog, &tried, &e) {
                    warn!("Provider {} failed, trying fallback {}", provider_id, fallback);
                    req.model = fallback;  // 切换模型
                    continue;
                } else {
                    return Err(e);  // 无更多 fallback
                }
            }
            Err(e) => return Err(e),  // 非可重试错误，直接失败
        }
    }
}
```

**配置示例**：
```toml
[[models]]
alias = "default"
provider = "anthropic"
model = "claude-sonnet-4-20250514"
failover = ["openai:gpt-4o"]  # 失败时切换

[[models]]
alias = "openai:gpt-4o"
provider = "openai"
model = "gpt-4o"
```

### 验收
- [ ] 单测：主模型返回 5xx，自动切换到 failover 模型
- [ ] 单测：failover 链耗尽，返回最后一个错误

### 成本
1-2 天（配置 schema + server 接线 + 单测）

## P2-9 向量语义检索接入 🟢 （功能增强，非必需）

### 背景
**现状**：
- `memory_vec` 表已建但 `trigger_vec` 列始终空
- Lane1 / standing intent 预筛都是纯词法（keywords contains）

**依赖**：需先定 embedding 模型（开放问题 1）

### 改动方案

#### 9.1 选择 embedding 来源
- **方案 A**：provider embedding API（如 OpenAI `text-embedding-3-small`）
  - 优点：质量高、维护成本低
  - 缺点：联网、成本（$0.02/1M tokens）
  
- **方案 B**：本地小模型（如 `sentence-transformers/all-MiniLM-L6-v2`）
  - 优点：离线、免费
  - 缺点：需集成 Python 或 ONNX runtime、维护成本高

**推荐**：方案 A（单用户成本可控，$1/月足够）

#### 9.2 接入流程
```rust
// 记忆写入时生成 embedding
pub async fn upsert_memory(&self, m: NewMemory) -> StoreResult<MemoryId> {
    let mem_id = self.write(|conn| ops::upsert_memory(conn, &m)).await?;
    
    // 异步生成 embedding（失败不阻塞主流程）
    let emb = self.embedding_svc.embed(&m.text).await.ok();
    if let Some(vec) = emb {
        self.write(|conn| {
            conn.execute(
                "INSERT INTO memory_vec(memory_id, embedding) VALUES(?, ?)",
                params![mem_id, vec],
            )
        }).await.ok();  // 失败仅记日志
    }
    
    Ok(mem_id)
}
```

#### 9.3 Lane1 改走向量预筛

- [ ] 记忆写入时自动生成 embedding（`memory_vec` 表有数据）
