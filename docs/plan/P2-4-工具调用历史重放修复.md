# P2-4 — 工具调用历史重放修复

> 制定日期：2026-09-08。
> 起因：真机复现「模型宣布要干活然后停手，不发工具调用」，连续两次。

## 1. 症状

用户让生成一份三国演义人物介绍 PPT，模型回一句「我直接写生成脚本
（古典风、16:9，封面+目录+背景+魏蜀吴人物+结语），然后运行:」就收尾了，
没有任何工具调用。换个说法重试，同样停在类似位置。

daemon 日志（`reason=Stop` 是关键）：

```
构建模型请求 msg_count=61 orig_count=85 tools=9
  shape=ast:96,usr:4172,ast:84,usr:53,usr:5384,ast:93,usr:609,ast:114,usr:4774,
        ast:115,usr:6832,ast:1443,…
上下文压缩已应用 dropped=24 pruned=0
模型轮结束 reason=Stop acc_chars=58
run 完成 ms=26851
```

排除项：
- **不是截断**。`reason=Stop` 是模型自己收尾，非 `Length`。
- **不是没给工具**。`tools=9`，且 [openai.rs:104](../../crates/oc-llm/src/openai.rs) 带了 `tool_choice: "auto"`。
- **不是超时/崩溃**。run 正常完成，26.8s 花在 thinking 上。

## 2. 根因：历史重放教会模型「宣布完就等人贴结果」

`shape=` 那行里**没有一条消息带 `+tc` 标记**（[run.rs:304](../../crates/oc-server/src/run.rs) 会给带
`tool_calls` 的消息打这个标记）。61 条历史，零工具调用结构。

两处联合造成：

**落库丢结构。** `entry` 表只有 `role` + `content`（[schema.rs:13](../../crates/oc-store/src/schema.rs)），
没地方存 `tool_calls`。[run.rs:150](../../crates/oc-server/src/run.rs) 落 assistant 时只写 `acc`
（工具调用前那句开场白），调用本身丢弃。

**重放改角色。** [session.rs:590](../../crates/oc-server/src/session.rs) 把工具结果降级成
`user` 消息 + `【历史工具结果】` 前缀。

于是模型看到的自己的历史是：

```
assistant: 装好了。现在写生成脚本…              （96 字）
user:      【历史工具结果】…pip 输出 4172 字…
assistant: 没挂，我在。刚才…                     （84 字）
user:      【历史工具结果】…5384 字…
assistant: 确认 PPT 还没生成。我现在在写脚本…     （93 字）
user:      【历史工具结果】…4774 字…
```

那些 4172 / 5384 / 4774 / 6832 字的巨型 `usr:` 全是被改头换面的工具输出。

**模型在自己的上下文里从没见过一次「我发起工具调用」的样例。** 它见过二十多次的
模式是「我宣布要做什么 → 然后用户把输出贴给我」。这是标准的 in-context learning：
上下文里最一致的模式压倒了系统提示词里的工具说明。所以它照着学——宣布，然后
`Stop`，等用户贴结果。

**这个坑自我强化**：每失败一轮，历史里的错误样例就多一条，下一轮更不会调工具。

附带损伤：`pruned=0`。剪枝只认 `MsgRole::Tool`（[run.rs:239](../../crates/oc-server/src/run.rs)），
而重放已把工具结果改成了 `User`，所以**剪枝对历史里的工具输出永久失效**——
那些几千字的 blob 只能整条丢（`dropped=24`），要么全留要么全扔。

## 3. 方案取舍

围绕「持久层是扁平 `role + content`、协议需要工具结构」这个矛盾，可选做法与结论：

| 做法 | 是否采用 | 理由 |
|---|---|---|
| 工具结构 JSON 编码进 `content`，重放时试解析还原 | ✗ | 改用真列，见下 |
| `entry` 表加 `tool_calls` / `tool_call_id` 真列 | ✓ | 直白、可查询、无解析容错分支 |
| 孤儿工具消息清理（配对断了就成对删） | ✓ | 拆散配对会让 provider 400 |
| 旧工具往返折叠成一句占位，保形状丢 payload | ✓ | 复用现有剪枝，无需新代码 |
| 降级只在原生工具关闭时才做，不无条件降级 | ✓ | 本次修复的核心语义变化 |
| `tool_call_id` 按各后端契约重映射 | ✗ | 当前只对接 OpenAI 兼容协议，过度设计 |

**不走 JSON 信封的理由**：那套做法适合没有持久层、历史只在进程内存里的架构。
本项目有 SQLite 持久层且开发阶段可随时删库（见 §7），加真列的成本比在 `TEXT`
里塞 JSON 再写解析容错更低。

## 4. 改动

### 4.1 落库能存工具调用结构

开发阶段不做迁移（见 §7）：**直接改建表 DDL，不加迁移步进**。

**`crates/oc-store/src/schema.rs`** — `V1` 的 `CREATE TABLE entry` 加两列：

```sql
CREATE TABLE entry (
  ...
  tokens_est    INTEGER NOT NULL,
  tool_calls    TEXT,          -- assistant 发起的调用（JSON 数组），NULL = 无
  tool_call_id  TEXT,          -- tool 结果关联的调用 id，NULL = 非工具结果
  created_at    INTEGER NOT NULL,
  ...
);
```

`TARGET_VERSION` 保持 2，`migrate.rs` 不动。删库后 `oc doctor` 按新 DDL 重建。

**`crates/oc-store/src/types.rs`** — `NewEntry` 与 `Entry` 各加两个
`Option<String>` 字段（同名）。

**`crates/oc-store/src/ops.rs`** — `append_entry` 的 INSERT 与 `load_transcript`
的 SELECT 带上新列。

### 4.2 run 落库时写入结构

**`crates/oc-server/src/run.rs`**

- `persist()` 签名扩展，接受 `tool_calls` / `tool_call_id`（或改为收 `NewEntry`）。
- [run.rs:150](../../crates/oc-server/src/run.rs) 落 assistant 时带上本轮的
  `ToolCallSpec`（序列化成 JSON）。当前 `acc` 为空也要落——否则纯工具调用轮
  在历史里彻底消失。
- [run.rs:176](../../crates/oc-server/src/run.rs) 落工具结果时带上 `call_id`。

### 4.3 重放还原原生结构

**`crates/oc-server/src/session.rs`** — `load_history`（约 585 行）：

- `Role::Assistant` + `tool_calls` 非空 → 反序列化回 `Vec<ToolCallSpec>`，
  产出带 `tool_calls` 的 assistant 消息。
- `Role::Tool` + `tool_call_id` 非空 → 产出原生 `MsgRole::Tool` 消息，带 id。
- **两者任一缺失才走现有降级**（`【历史工具结果】` + `user`）。降级从「无条件」
  变成「兜底」，这是本次修复的核心语义变化。

### 4.4 压缩不能拆散工具对

**`crates/oc-core/src/compaction.rs`**

`assistant(tool_calls) → tool(result)` 是协议上的原子对，拆开任一半都会让
provider 400。而 `plan.drop` 按预算从最早开始逐条丢，会拆。

memclaw 每轮**恒定只有一个工具调用**（[run.rs:457](../../crates/oc-server/src/run.rs)
返回单个 `ToolCall`；[openai.rs](../../crates/oc-llm/src/openai.rs) 只执行 index=0），
且结果紧跟其后入队。所以配对是**位置相邻**的，不必引入 id 匹配：

- `MsgMeta` 加 `is_tool_dispatch: bool`（该 assistant 发起过调用）。
- `plan_compaction`：丢弃 `i` 时若 `is_tool_dispatch` 则连带丢 `i+1`；
  丢弃工具结果 `i` 时若 `i-1` 是 dispatch 则连带丢 `i-1`。成对进出，预算记账
  也按对算。

同时 4.3 修好后 `is_tool_result` 判定自然复活（角色不再被改写），
剪枝重新生效——巨型 blob 会被截到 `prune_to_tokens`（默认 200 token）并加
`…[旧工具输出已剪枝]` 尾注，保住「这里调过工具」的形状，丢掉 payload。
即 §3 里那条「折叠占位」，用现有机制即可，无需新代码。

### 4.5 提示词补一句（可选）

**`crates/oc-core/src/prompt.rs`** — [第 134 行](../../crates/oc-core/src/prompt.rs)
那段工具引导只讲「优先用哪个工具」，没讲「宣布之后要在同一轮真的调用」。

正常情况下不需要这句。但 [prompt.rs:69](../../crates/oc-core/src/prompt.rs) 的注释
已记着同一个模型（`doubao-seed-evolving`）无视系统提示词、编造自身型号的前科——
它对 in-context 模式的依赖强于对指令的服从。加一句成本极低，作为纵深防御。

## 5. 验证

单测（已落地，321 项全绿）：
- `oc-store`：`entry_roundtrip_keeps_tool_structure` —— 两列可写可读，且**空
  content 的纯工具调用轮也落库**。
- `oc-core::compaction`：`drops_tool_pairs_together`（成对进出）、
  `never_orphans_result_inside_keep_recent`（结果在保护区时整对不动）。
- `oc-core::memory`：`empty_assistant_tool_dispatch_does_not_consume_pending_user`
  —— 空文本 assistant 落库后不能抢走待配对的提问（见 §8）。
- `oc-server/tests/tool_history_replay.rs` 5 项：原生结构重放、老记录仍降级、
  孤儿结果整条删、悬空 dispatch 摘 `tool_calls`、真跑一轮工具后重启重放。

真机（这是唯一能证明修好的验证，单测覆盖不到 in-context learning）：
1. 删库（见 §7，**必做**：老库没有新列，读历史会直接失败），起 daemon。
2. 同一个 PPT 任务跑一遍，`grep "构建模型请求" ~/.oc/logs/oc.log.$(date +%F)`
   看 `shape=` 里**出现 `ast+tc:` 标记**。
3. 确认 `reason=ToolUse` 而非 `Stop`，且 PPT 真的生成了。

## 6. 已有历史怎么办

库里那 85 条历史**补不回 `tool_calls`**——当时就没存。它们仍会走降级路径，
错误样例继续留在上下文里。两个选择：

- `/session ppt2` 换新会话（历史清零，立即可用）
- 删库重来（见 §7）

顺带：这也是一个**低成本的诊断验证**——如果换新会话后模型正常调工具，
就坐实了「问题在历史污染」这个判断。建议在动手改代码前先跑这一步。

## 7. 删库重建（本阶段约定）

开发阶段**不做任何数据迁移**：改表结构直接改建表 DDL，不写迁移步进、不写
兼容分支。

```bash
# daemon 必须先停（单实例锁 + WAL）
sudo systemctl stop oc-daemon     # 或 Ctrl-C
rm ~/.oc/oc.sqlite*               # 连 -wal / -shm 一起删
oc doctor                         # 按新 DDL 重建
```

等项目进生产阶段（有真实用户数据不能丢时）再改这个约定，届时需要补回
`migrate.rs` 的前向步进纪律。

## 8. 实施记录（2026-09-08 完成）

按 §4 全部落地，`TARGET_VERSION` 仍为 2、`migrate.rs` 未动。两处方案里没写到、
动手后才暴露的东西：

**`plan_compaction` 的保护区边界。** dispatch 在可动区末尾、它的结果落在
`keep_recent` 里时，按方案「丢 i 就连带丢 i+1」会把近期消息拽走，破掉
`keep_recent` 的硬承诺；只丢 dispatch 又留下孤儿。取第三条路：**整对都不动**，
预算从更早的消息里腾。

**空 content 的 assistant 落库后污染了记忆提取。** 纯工具调用轮现在会落库
（否则历史里缺 dispatch 那一半），而 `extract_episode_candidates` 见到 assistant
就取走待配对的 user——于是配出「提问 + 空回答」，真正的回答反倒成了孤立条目。
修法是在提取侧跳过空文本 assistant 且**保持 `pending_user` 挂起**，让提问去等
工具轮结束后真正回答它的那条。这是本次改动唯一的跨模块副作用。

另外把 `NewEntry::text()` 构造器加上了：新增两列后 16 处字面量都要补
`tool_calls: None, tool_call_id: None`，绝大多数是纯文本记录，走构造器更干净。
