# 05 — 下一阶段计划

> 制定日期：2026-08-29。权威设计源：[04-详细设计文档.md](../design/04-详细设计文档.md)。
> 本文把「设计承诺 vs 已落地」的缺口 + 近期实战暴露的问题，收敛成一份可执行的阶段计划。
> 每完成一项，勾掉并在末尾变更记录追加一行。

## 0. 现状与指导原则

M1–M6 主体已落地：对话 / 持久化 / 记忆检索(Lane1) / 防卡死 / 工具+审批 / cron 主动性 / CLI。
但近期（2026-08-29 前后）实战暴露：**咬人的问题全在核心对话闭环里**——工具调用空回复、
输出截断、abort 失灵。设计文档的缺口清单只跟踪「功能没接线」，没跟踪「核心路径不稳」。

**指导原则**：在会丢事件、abort 不生效的对话路径上堆功能，等于流沙盖楼——每个新功能都继承
这份 flaky，且更难 debug。因此本计划排序为：

```
P0 稳定核心闭环  →  P1 补齐助手功能  →  P2 生产化收口
（发消息/工具/中止可靠）  （像个完整助手）    （能长期挂着、可发布）
```

已具备的排查抓手：本轮已落地结构化日志（`~/.oc/logs/`）+ `oc debug` 运行时快照，
P0 的问题可先用日志复现验证根因，再动手，避免猜。

## P0 — 稳定核心闭环（最高优先）

来源：2026-08-29 线程安全排查（三 crate 分头审）。结论是**无经典死锁/数据竞争**，
DashMap 用法规范、actor 隔离良好；真正的风险是**事件丢失**和**审批路径**。

### P0-1 事件丢失（极可能是「截断」根因）🔴 ✅ 已完成（2026-08-31）
> **落地**：采用「per-run 背压流」（方案 B，见 [06-zeroclaw流式传输调研.md](../research/zeroclaw流式传输调研.md)）。
> 新增 `RunSink`（[sink.rs](../../crates/oc-server/src/sink.rs)）：run 内联事件（Assistant/
> Lifecycle/Tool/Approval）改走每 run 专属、有界、背压的通道，经 `RunSink::Conn` 定向
> 回发到发起连接的出站队列；慢客户端 → 背压挂起（driver select cancel，不锁车道）→
> 不丢字。broadcast 瘦身到仅 Usage/Proactive（低频、不会 Lagged）。
> 回归测试 `long_reply_not_truncated`：400 delta 经真实连接完整送达。
- **现象**：长回复中途截断、消息不完整——本周多次遇到。
- **根因（两处叠加）**：
  - broadcast 容量固定 256（[lib.rs](../../crates/oc-server/src/lib.rs) `EVENT_CHANNEL_CAP`）。流式回复每 token
    一个 `Assistant` delta，长回复轻松超 256；任一慢连接拖慢转发即 `Lagged`，丢失的事件**永久丢失**。
  - 每连接转发任务 `try_send` 失败**静默丢帧**（[conn.rs](../../crates/oc-server/src/conn.rs)），不断连、不告警。
- **修法**：
  1. 先用日志复现确认：长回复时 `conn.rs` 是否真的 `Lagged`/丢帧（加计数日志）。
  2. delta 事件合并/批处理，降低事件频率（一次 flush 多个 token）。
  3. `Lagged` 后触发一次状态重同步（重新拉当前 run 完整文本）而非放任缺口；
     慢连接宁可断连也不静默丢。
- **验证**：构造 >256 token 的长回复，确认 TUI 完整收到。

### P0-2 CancellationToken 打断不了正在等待的审批 🟠 ✅ 已完成（2026-08-31）
> **落地**：工具侧 [exec.rs](../../crates/oc-tools/src/exec.rs) 的 `gate.ask().await` 套
> `select!` + `cancel.cancelled()` → 返回 `Aborted`；server 侧审批等待
> （[tools_bridge.rs](../../crates/oc-server/src/tools_bridge.rs) `request_approval`）同样
> `select!` 叠 cancel。回归测试 `abort_interrupts_pending_approval_and_cleans_registry`
> 验证 abort 立即释放车道（<2s）。
- **现象**：用户发 abort（或看门狗判卡死）时，run 卡在 `gate.ask().await` 不释放车道，abort 看似失灵。
- **根因**：审批等待没有 select 在 cancel 上（[run.rs](../../crates/oc-server/src/run.rs) 的 `exec_tool().await` 未套 cancel；
  [exec.rs](../../crates/oc-tools/src/exec.rs) 的 `gate.ask().await` 无取消守卫）。
- **修法**：审批等待 `tokio::select!` 叠加 `cancel.cancelled()` → 返回 `Aborted`；
  `ApprovalGate::ask` 观察 cancel token。

### P0-3 审批 registry entry 泄漏 🟠 ✅ 已完成（2026-08-31）
> **落地**：[tools_bridge.rs](../../crates/oc-server/src/tools_bridge.rs) 引入 `ApprovalGuard`
> RAII 守卫，按 approval_id 在 drop 时清理 registry，覆盖所有退出路径（正常回执/超时/
> abort/pump 被 abort）。同回归测试断言 abort 后 `registry.is_empty()`。
> 顺带简化：删除 `ApprovalHandler` trait 与 `EventApprovalHandler`（审批逻辑内聚到
> `ToolExecutor::run`，registry 与 ServerState 共享）。
- **根因**：超时/abort 导致 `rx.await` 被 drop 时，`ApprovalRegistry` 里的 entry 不清理
  （[tools_bridge.rs](../../crates/oc-server/src/tools_bridge.rs) 只在 channel-closed 分支 remove）。长期运行无界增长。
- **修法**：用 RAII guard（按 approval_id）或每个退出路径都 remove。

### P0-4 阻塞 IO 跑在 async executor 上 🟠 ✅ 已完成（2026-08-31）
> **落地**：[file.rs](../../crates/oc-tools/src/file.rs) 的 `grep`/`glob` 包
> `tokio::task::spawn_blocking`，同步遍历不再霸占 tokio worker，工具级 30s 超时也对其生效。
- **根因**：`grep`/`glob`（[file.rs](../../crates/oc-tools/src/file.rs)）用同步 `walkdir`/`std::fs`/`canonicalize`，
  直接在 async `invoke` 里跑；大目录会卡住整个 tokio worker，拖累所有会话。
- **修法**：包 `tokio::task::spawn_blocking`。工具 30s 超时对同步阻塞代码也不生效，一并解决。

### P0 出口标准
发消息、工具调用、中止 三条基础路径可靠：长回复不截断、abort 立即释放车道、
大目录工具不冻结其它会话、长期运行审批表不泄漏。这是后续一切的地基。

  没有显式日预算。真机观察成本后再定，见下方 P2 待办。

### P1-5 定时/延时提醒引导至 cron 🟠（2026-08-31 真机实测暴露）
- **现象**：用户说「12:50 提醒我喝水」，模型**不用已有的 cron 能力**，而是想在一次 run 内
  **同步阻塞等到 12:50**——反复调 `sys:now` 查时间 + `powershell Start-Sleep`/`timeout /T`
  硬凑「等待」，6 轮工具调用约 76 秒后触发 loop detection、判 `LoopDetected` 中止，提醒没设成。
  （日志：`~/.oc/logs` 中 run `01a05626-0dda`，第 622–653 行。）
- **根因（两层）**：
  1. **能力认知缺失**：cron 定时任务能力已实现（[proactive.rs](../../crates/oc-server/src/proactive.rs) + `cron.add`），
     但模型不知道该用它、也没有可直接调用的 cron 工具，于是选了「run 内干等」这条错路。
  2. **shell 等待不可靠**：PowerShell `Start-Sleep` 在测试机上「只回显不执行」，模型反复换命令试
     → 撞 loop detection。此故障是①的次生，①修好后该路径不会被触发。
- **修法（方向）**：
  - **主**：把 cron 引导进模型决策——系统提示明确「定时/延时/未来某时刻的提醒用 cron，
    不要用 shell 睡眠阻塞等待」；并考虑把 cron.add 暴露为模型可直接调用的工具（现仅 CLI/proto）。
  - **副**：给模型一个可靠的「延时/定时」原语，替代拿 shell 硬凑。
- **归类说明**：run 循环 / 事件流 / 审批 / loop detection 本次**均按设计正确工作**（loop detection
  正确兜住了打转，未无限空转）。这不是 P0 代码回归，是上层「助手能力/引导」缺失，属 P1 范畴。
- **验证**：「X 时提醒我做 Y」应秒设为 cron 定时任务并即时反馈，而非阻塞 run 干等。

### P1-6 episodic 记忆产出（§11.5 flush）🔴 dreaming 的上游断点
- **现象**：**dreaming 在真机上永远空转**。P1-4 把巩固模型轮做完了，但整条链的
  上游是断的——全仓**没有任何代码写入 `tier='episodic'`** 的记忆，而
  `dream_candidates` 只取 episodic。所以正常聊天不会积累出任何候选，
  每轮 dreaming 扫描都是空集直接返回。
- **现状核对**（2026-09-01 写 P1-4 测试用例时发现）：
  | 环节 | 状态 |
  |---|---|
  | 产生 episodic 候选 | ❌ **无人**（设计 [§11.5](../design/04-详细设计文档.md) 未落地） |
  | `dream_candidates` 取候选 | ✅ |
  | 双门判定 + tier 提升 | ✅ |
  | 巩固模型轮重写 MEMORY.md | ✅ P1-4 |

  唯一的记忆写入路径是 `persist_explicit_memory`（用户显式"记住…"），它直接写
  **curated**，绕过了 episodic → 巩固这条路。
- **改动**：落地设计 §11.5——`session.reset` 或压缩（`compact`）触发前，把当前会话中
  「值得记住」的内容 flush 为 episodic 候选。判定用纯函数（哪些算值得记住），
  IO 在 store，调度在 session。
- **为何是 P1**：不做的话 P1-4 的巩固能力**在真实使用中等于不存在**——只能靠手工
  塞数据验证（见 [P1-4 测试用例](../testing/P1-4-dreaming重写MEMORY测试用例.md) §0.4）。
  「睡眠巩固名副其实」这条 P1 出口标准实际未达成。
- **依赖**：与压缩路径（`summarize`）耦合，建议在动压缩逻辑时一并做。
- **验证**：聊够多轮触发压缩 → 查库应出现 `tier='episodic'` 的行 → 等其满足双门
  （importance/use_count/≥3 天）后 dreaming 自然巩固，无需手工造数据。

### P1 出口标准
项目达到设计文档承诺的「完整助手」形态：能主动提问、记住偏好并覆盖矛盾、
待办能在相关对话中被唤起、睡眠巩固名副其实。

> ⚠️ 最后一条（睡眠巩固）**尚未真正达成**：P1-4 的巩固链已完整，但上游无人产出
> episodic 候选（见 P1-6），真机上 dreaming 始终空转。P1-6 完成后该项才算闭环。

## P2 — 生产化收口

让它能长期挂着跑、可对外发布。多为技术债与工程化。

| 项 | 现状 | 来源 |
|---|---|---|
| **读写分离**（读走独立连接池 + spawn_blocking） | 读写共用单写线程，慢查询阻塞全体会话；与 [04 §3.1](../design/04-详细设计文档.md) 矛盾 | 排查 HIGH-1 |
| **memory.text 索引**（FTS5 或高频列索引） | `LIKE '%term%'` 全表扫描 | 排查 HIGH-1 |
| **写线程 panic 自愈** | JoinHandle 被丢弃、无监控；线程死后存储层瘫痪需重启 | 排查 MEDIUM-1 |
| **idem 幂等缓存 TTL/LRU** | 无淘汰，长期运行内存单调增长 | 排查 MEDIUM-1(server) |
| **会话 actor 空闲淘汰** | actor 永不退出，大量随机 session id 会累积 | 排查 MEDIUM-2(server) |
| **ArcSwap 代际快照 / 配置热更** | 仅注释，无 ArcSwap 使用 | [04 §4.4/§4.8] |
| **provider failover 接线** | `failover_plan`/`resolve_alias` 就绪但无调用方 | [04 §4.6] |
| **双平台 CI matrix** | 无 CI；unix socket 仅编译未在 Linux 实跑 | [04 §14] M2 硬验收 |
| **oc-core::context 模块** | 上下文加载散在 server::session | [04 §15] M5 |
| **向量语义检索** | sqlite-vec feature 默认关，当前纯词法 | [04 §4.5] |
| **tokenizer 精度** | 字符/4 近似，tiktoken 未接 | [04 §16] |
| **path_guard TOCTOU / 文件写原子性 / 后台输出 channel 无界** | 个人助手信任模型下影响低 | 排查 LOW |

### 语义偏差（择机修正）
- **cron day-of-month / day-of-week**：标准 cron 两者非 `*` 时取 OR，当前实现取 AND
  （个人助手场景多数只用其一，已注明）。

## 执行顺序建议

1. **P0-1**（事件丢失）——先复现验证，它极可能就是本周「截断」根因，收益最直接。
2. **P0-2 + P0-3**（审批取消 + 泄漏）——一组，逻辑集中。
3. **P0-4**（阻塞 IO）——独立小改。
4. → P0 出口验证后，进 **P1-1**（ask_user，复用 P0-2/3 的通道）。
5. P1 其余（标注纯函数就绪的接线项，成本小）。
6. P2 按需排期：读写分离 / 写线程自愈优先（可用性瓶颈），其余生产前收口。

**当前位置（2026-09-01）**：P0 + P1-1~P1-4 已落地，剩 **P1-5**（cron 引导，真机暴露的
助手能力缺失）与 **P1-6**（episodic 产出，dreaming 的上游断点）。

建议接下来：
- **先真机跑一遍 P1-2/P1-3/P1-4**（用例见 [testing/](../testing/)）。四项 P1 至今**只有
  自动化验证**；历史上 P0-1 与 P1-1 的缺陷都是真机才暴露的，攒着不验风险累积。
- 然后 **P1-6**（让 dreaming 真正跑起来，P1-4 才有意义）或 **P1-5**（真机已暴露、
  用户可感知的能力缺失）。两者独立，可按体感优先级选。

> 注：P0/P1 每项落地后，同步更新 [04 §15](../design/04-详细设计文档.md) 的落地状态与本文件勾选。
