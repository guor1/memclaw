## 二、「15 个测试文件」的真相

**看起来吓人，实则每个文件只改 1–3 行。**

```rust
// 改动前（tests/antistuck.rs）
SessionConfig {
    ...
    trigger_max_per_turn: 3,
    context_window: 65536,
}

// 改动后
SessionConfig {
    ...
    trigger_max_per_turn: 3,
+   intent_defaults: Default::default(),  // 新增这一行
    context_window: 65536,
}
```

**为什么必须改**：  
`SessionConfig` 新增字段 `intent_defaults: IntentDefaults`（包含 cooldown/budget/expiry_days/max_per_turn 四项，
用 `IntentDefaults` 结构体聚合），Rust 要求所有测试构造 `SessionConfig` 时也必须提供该字段，否则编译不过。

**已验证**：每个文件改动行数 = 1–3 行（antistuck/toolloop/roundtrip 有多个 cfg 构造点，其余都是 1 行）。  
**无隐患**：`Default::default()` 生成默认值（24h/3 次/90 天/≤3 条），与既有测试场景无关，不影响其测试意图。

## 三、核心改动（真正的「功能代码」）

### 3.1 store 层（4 文件，~180 行新增）

| 文件 | 改动 | 风险评估 |
|---|---|---|
| **ops.rs** | +`intent_add/list/rm/mark_fired` + keywords 编解码（换行分隔） | ✅ 纯 SQL，模式照搬 `cron_*`，已有 3 项往返测试覆盖 |
| **writer.rs** | +4 个 `WriteCmd` + 4 个 async 方法 + run_loop 分派 | ✅ 单写线程 actor 标准模式，与既有 28 个命令同构 |

| **lib.rs** | +3 项往返测试（含含空格关键词回归） | ✅ 测试代码，不影响运行时 |

**隔离性**：store 层对外暴露的 4 个新 API（`intent_add/list/rm/mark_fired`）只被 `session.rs::intent_scan` 和 `dispatch.rs::handle_intent_*` 调用，**不与既有 cron/memory/entry 路径交叉**。

### 3.2 session 层（1 文件，~125 行核心逻辑）

**`session.rs::intent_scan`**（新增函数，触发链核心）：
- 在 `begin_run` 里调用，位置：`load_history` 之后、`start_run` 之前。
- 逻辑：`intent_list` → `intent_prefilter`（纯函数） → 逐条 `allow_fire`（纯函数） → 允许则注入 `MemLine` + `intent_mark_fired` + 审计。
- **失败绝不阻塞**：任何步骤出错返回空 `Vec`、只告警，与 `lane1_bootstrap` 同规格。
- **隔离性**：只在主会话的 `begin_run` 触发；cron/dreaming 走隔离子会话（`proactive.rs::run_isolated_turn`），不经 `begin_run`，**天然避免误注入**。

**风险点排查**：
1. **会否阻塞正常回复**？  
   ✅ 失败路径全 `warn!` + 返回空，不 panic、不 await 无限等待。
2. **会否与 Lane1 记忆注入冲突**？  
   ✅ 都追加到同一个 `Vec<MemLine>` 里，按 `key` 排序后一起注入 prompt（`prompt.rs` L104），无冲突。
3. **会否被 cron/dreaming 误触发**？  
   ✅ 只在 `begin_run` 调用，cron 走 `proactive.rs::run_isolated_turn`（不调 `begin_run`），dreaming 同理（子会话）。

### 3.3 dispatch 层（1 文件，~93 行）

**3 个 handler**：`handle_intent_add` / `handle_intent_list` / `handle_intent_rm`。
- 照抄 `handle_cron_*` 模式：校验参数 → 读 `ServerState::intent_defaults` → 调 store。
- 参数校验：text 非空、keywords ≥1 条非空（否则 `BadRequest`）。
- **隔离性**：新增 3 个 `Method` 枚举值（`IntentAdd/List/Rm`），不与既有 20+ 个 Method 交叉。

**风险点排查**：
1. **会否影响既有 Method 路由**？  
   ✅ `match method` 新增 3 个 arm，既有分支不变。
2. **会否破坏 `ServerState` 并发安全**？  
   ✅ 只读 `state.intent_defaults()`（`&self`），不改 state；store 调用走单写线程 actor。

### 3.4 配置层（2 文件）

**oc-core/config.rs**：
- `ProactiveConfig` 新增 `intent_max_per_turn: u32`（带 `#[serde(default)]`）。
- **向后兼容**：老 config.toml 缺该键时回落到默认 3，不报错（已有测试覆盖）。

**oc-cli/provider_setup.rs**：
- 从 `ProactiveConfig` 读 4 个键灌入 `IntentDefaults`，传给 `ServerState`。
- **接上此前死键**：`intent_cooldown_secs` / `intent_budget` / `intent_expiry_days` 三个配置键此前定义了但没人读，本次才真正接上。

**风险点排查**：
1. **老配置会否炸**？  
   ✅ `#[serde(default)]` 兜底 + 测试覆盖（`config_loader.rs::old_config_without_intent_max_per_turn_still_loads`）。
2. **新配置会否破坏既有启动**？  
   ✅ 默认值（24h/3 次/90 天/≤3 条）保守，不影响既有行为（standing intent 表初始为空，不触发任何扫描）。

## 六、复查抓到的两个 bug（已修）

### Bug 1：keywords 空格分隔导致含空格关键词被劈开 🐛

**症状**：用户建 `oc intent add "订机票" "business trip"`，关键词 `business trip` 是**一个词**，
但落库用空格分隔、取回时被 `split_whitespace` 劈成 `business` / `trip` 两条。结果用户只说 "trip"
就触发——**触发面比用户指定的宽**。

**隐蔽性**：往返测试"字没丢"，但**值变形了**——`["business trip"]` 变成 `["business", "trip"]`，
测试断言 `!keywords.is_empty()` 仍然通过。

**已修**：改用**换行分隔**（`\n`），编码时把关键词内部空白归一为单空格（清掉可能混入的换行），
保证分隔符唯一。补回归测试 `intent_keyword_with_space_survives_roundtrip`。

### Bug 2：expiry 绝对/相对换算时哨兵值与钳位冲突 🐛

**症状**：store 存**绝对时间点** `expiry_at`，core 收**相对时长** `expiry_secs`，而 `expiry_secs == 0`
的语义是**永不过期**。我最初用 `(at - created).max(0)` 换算，于是「已过期」（差值 ≤0）被钳成 0 →
静默翻转成「永不过期」，过期待办反而永远触发。

**已修**：差值 ≤0 直接判过期跳过，不进 `NagCfg`（不让哨兵值 0 经过 `max(0)`）。

**教训**：跨层语义换算时，哨兵值与钳位操作会冲突；"往返不丢字"≠"往返不变形"。

## 八、改动范围合理性判断

**结论：改动范围大，但每一处都是必要的，无冗余。**

### 为何「看起来多」？

1. **15 个测试文件**：机械式补字段（每个 1 行），不改属编译错误。
2. **全栈改动**（store → proto → server → cli）：这是「新增一张表 + 3 个 Method」的标准代价——
   你的架构本身就是分层的，加新功能必然垂直穿透各层。
3. **配置接线**：3 个死键 + 1 个新键，4 处配置文件（core/cli/onboard/example）都要改。

### 与既有功能（cron）对比

| 功能 | 文件数 | 改动模式 |
|---|---|---|
| **cron（时间触发）** | 同样全栈（store/proto/server/cli） | P0 落地时同样改了 30+ 文件 |
| **standing intent（话题触发）** | 34 改 + 2 新 | 与 cron 同规模，符合预期 |

**差异**：cron 触发在隔离子会话（`proactive.rs`），intent 触发在主会话 `begin_run`——但两者**不交叉**。
