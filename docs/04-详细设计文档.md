## 1. 架构总览

### 1.1 一句话心智模型

`oc serve` 起一个常驻进程（daemon），进程里有**一个编排层（oc-server）**协调四类下游：纯策略（oc-core）、持久化（oc-store）、模型（oc-llm）、工具（oc-tools）。用户通过本地 socket 连上，`oc`(TUI) 是协议的第一个 client。整个进程服务**唯一用户的唯一主会话**，外加若干**隔离子会话**（cron 触发 / dreaming / Lane2 检索）。

### 1.2 进程内组件拓扑

```
┌─────────────────────────── oc (进程) ────────────────────────────┐
│                                                                   │
│   client(s) ──socket──►  ProtocolServer (oc-server)               │
│                              │                                    │
│                              ▼                                    │
│                          Dispatcher ──► IdempotencyCache          │
│                              │                                    │
│              ┌───────────────┼────────────────┐                  │
│              ▼               ▼                ▼                   │
│         SessionActor    Scheduler        TaskLedger               │
│        (主会话车道)     (心跳/cron堆)     (后台任务台账)             │
│              │               │                                    │
│              ▼               ▼                                    │
│          AgentLoop ◄─── (隔离子会话: cron/dreaming/Lane2)         │
│         (oc-core状态机)                                            │
│         │    │      │                                             │
│         ▼    ▼      ▼                                             │
│    oc-llm  oc-tools oc-store  ◄── WriterActor(单写线程) ── SQLite  │
│                       │                                           │
│                    oc-core::memory (纯策略) 供排名/预筛/双门判定    │
└───────────────────────────────────────────────────────────────────┘
        EventBus (tokio broadcast) ──► 所有 client 的 event 帧
```

### 1.3 依赖方向（单向无环，编译期强制）

```
oc-cli ─► oc-tui ─► oc-server ─► oc-core   (纯策略, 无 IO)
                       │  │  │
                       │  │  └► oc-store   (持久化 + SQL/向量执行)
                       │  └───► oc-tools ─► oc-llm
                       └──────► oc-llm
        oc-proto  ◄── (oc-server / oc-tui / oc-cli 共享 DTO)
```

- **oc-core 不依赖任何其它 oc-\* crate**（除 oc-proto 中的纯数据类型，若需要）。它只输出决策，不执行。
- **oc-store 不依赖 oc-server**：store 暴露 trait + 实现，server 调用。
- **循环依赖靠 `cargo` workspace 依赖图在编译期挡住**；review 时任何"core 里 import tokio/rusqlite"都是红线。

### 1.4 三条并发主线

| 主线 | 载体 | 生命周期 | 卡死兜底 |
|---|---|---|---|
| **主会话车道** | 单个 `SessionActor` + 有界队列 | 进程存活期 | 空闲看门狗 / run 超时 / abort-drain（§10） |
| **调度线** | `Scheduler` 持最小堆（下次触发时间） | 进程存活期 | tick 回调各自套 timeout |
| **子会话** | 每个隔离 `AgentLoop` 独立 spawn | 单次任务 | own timer + 到期 abort + 清理 |

主会话车道**串行**：同一时刻只有一个活跃 run，其余进队列。这是单用户假设带来的最大简化——不需要多 agent 路由、DM 隔离、车道池。

### 1.5 错误与 panic 边界

- 每个 run 在 `oc-server` 里以 `tokio::task` 承载，run 主体包一层 `catch_unwind`（要求 `panic="unwind"`，见落地方案 §7）。
- 单 run / 单工具 panic → 捕获 → 归一化为该 run 的**错误终态**（`RunOutcome::Panicked`）→ EventBus 推 `lifecycle(error)` → 车道释放。**进程存活**。
- store 的 `WriterActor` 若 panic，视为致命（数据完整性风险），走进程级降级：停止接受写、通知 client、保留只读。

## 2. oc-proto：交互协议

**职责**：定义 CLI/TUI↔daemon 的全部线上契约（DTO），生成 JSON Schema 作为未来渠道适配器的接入依据。**只有类型 + serde + schemars**，无逻辑、无 IO。

### 2.1 帧模型（三类，判别联合）

```rust
/// 顶层帧。tag = "kind"，让"不可能的状态无法表示"。
#[derive(Serialize, Deserialize, JsonSchema)]
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum Frame {
    Req(Req),      // client → server，期待一个 Res
    Res(Res),      // server → client，对某个 req 的应答
    Event(Event),  // server → client，主动推送，无对应 req
}

#[derive(Serialize, Deserialize, JsonSchema)]
pub struct Req {
    pub id: ReqId,               // client 生成，用于配对 Res
    pub method: Method,          // 判别联合，见 2.2
    #[serde(default)]
    pub idempotency_key: Option<IdemKey>, // 仅 side-effecting 方法要求
}

#[derive(Serialize, Deserialize, JsonSchema)]
pub struct Res {
    pub id: ReqId,               // 对应的 req.id
    pub result: Result<MethodOk, ProtoError>,
}
```

### 2.2 方法（MVP 最小集）

```rust
#[derive(Serialize, Deserialize, JsonSchema)]
#[serde(tag = "method", content = "params", rename_all = "snake_case")]
pub enum Method {
```

### 2.3 事件流（服务端推）

```rust
#[derive(Serialize, Deserialize, JsonSchema, Clone)]
#[serde(tag = "event", rename_all = "snake_case")]
pub enum Event {
    /// run 生命周期
    Lifecycle { run_id: RunId, phase: LifecyclePhase }, // Start|End|Error{msg}
    /// 流式回复增量
    Assistant { run_id: RunId, delta: String },
    /// 工具活动
    Tool { run_id: RunId, call_id: ToolCallId, phase: ToolPhase }, // Start{name,args_preview}|Update{chunk}|End{status}
    /// ★主动提醒推送（cron/intent 触发）
    Proactive { kind: ProactiveKind, text: String, source: ProactiveSource },
    /// 后台任务进展/完成
    Task { task_id: TaskId, update: TaskUpdate },
}

#[derive(Serialize, Deserialize, JsonSchema, Clone)]
#[serde(tag = "phase", rename_all = "snake_case")]
pub enum LifecyclePhase { Start, End, Error { message: String, kind: ErrorKind } }
```

### 2.4 契约要求（落地方案 §3.4 的具体化）

1. **全部 DTO 派生 `JsonSchema`**；`oc-proto` 提供 `export_schema() -> serde_json::Value`，`oc doctor --dump-schema` 落盘 `schema/oc-proto.json`。CI 校验 schema 无意外漂移（快照测试）。
2. **判别联合优先**：帧 / 方法 / 事件 / 终态一律 tagged enum，禁用"裸 Option 表状态"。
3. **幂等键**：`ChatSend`、`CronAdd` 等 side-effecting 方法带 `idempotency_key`（client 生成 UUIDv7）。server 端 `IdempotencyCache`（dashmap）在 TTL 内对同键返回首个结果，避免重连重放导致重复 run。
4. **版本字段**：`Connect` 带 `proto_version`（单个 u16）。单用户下不做 N-1 兼容协商，只做**硬校验**：不匹配直接拒连并提示升级。

### 2.5 传输与编解码

- **帧编码**：换行分隔 JSON（NDJSON）over stream；每帧一行。简单、可 `tokio::io::Lines` 读、便于抓包调试。
- **传输实现**：
  - Unix：`tokio::net::UnixListener`，socket 路径 `~/.oc/run/oc.sock`（权限 0600）。
  - Windows：命名管道 `\\.\pipe\oc-{user_sid}`。**AF_UNIX 与 named pipe 是两套 API**，`oc-server` 用 `enum Transport { Unix(...), Pipe(...) }` 抽象，各自实现 `AsyncRead+AsyncWrite`。
  - WS（feature `ws-remote`）：`tokio-tungstenite`，附带可选 bearer token。默认关。
- **背压**：每 client 一个发送队列（有界）；事件广播用 `tokio::sync::broadcast`，慢 client 丢事件（收到 `Lagged` 提示重新 `status` 拉全量快照），**绝不阻塞 run**。

## 3. oc-store：单库存储

**职责**：单库 `oc.sqlite` 装全部；schema 版本化 + 前向迁移；**单写线程**（WriterActor）；读连接可并发；`sqlite-vec` 向量索引。**store 只做持久化与查询执行，不做策略判定**（策略在 oc-core）。

### 3.1 连接与并发模型

- **一个专用写线程**：`WriterActor` 持有唯一可写 `rusqlite::Connection`（`PRAGMA journal_mode=WAL; synchronous=NORMAL; foreign_keys=ON; busy_timeout=5000`）。所有写通过 `mpsc` 命令队列串行执行。**贴合"事务内不 await"**：写线程是同步的，事务体内纯 rusqlite 调用，无 `.await`。
- **读**：WAL 下读不阻塞写。读走**短连接**（每次开/用/关）或小型读连接池（`Vec<Connection>` + `Mutex`，非 r2d2）。单用户并发低，简单即可。
- **对外接口**：`oc-store` 暴露 `Store` trait（异步方法），实现内部把写请求投递给 WriterActor 并 `oneshot` 等回执，读请求 `spawn_blocking` 跑 rusqlite。

```rust
#[async_trait]
pub trait Store: Send + Sync {
    // 会话 / transcript
    async fn append_entry(&self, e: NewEntry) -> Result<EntryId>;
    async fn load_transcript(&self, session: SessionId, budget: TokenBudget) -> Result<Vec<Entry>>;
    async fn reset_session(&self, session: SessionId) -> Result<()>;
    // 记忆
    async fn upsert_memory(&self, m: NewMemory) -> Result<MemoryId>;
    async fn rank_search(&self, q: RankQuery) -> Result<Vec<MemHit>>;   // 执行 §4 排名 SQL
    async fn vec_search(&self, emb: &[f32], k: usize) -> Result<Vec<VecHit>>;
    // 主动性
    async fn add_cron(&self, c: NewCron) -> Result<CronId>;
    async fn due_triggers(&self, now: OffsetDateTime) -> Result<Vec<Trigger>>;
    async fn list_intents(&self) -> Result<Vec<StandingIntent>>;
    // 台账 / 审批 / 配置状态
    async fn ledger_append(&self, rec: AuditRecord) -> Result<()>;
    async fn task_upsert(&self, t: TaskRow) -> Result<()>;
    // ...
}
```

### 3.2 迁移

- `migrations/NNNN_*.sql`，`user_version` PRAGMA 记录版本。启动时 `run_migrations()` **前向**逐步升级；**只前不后**（不写 down）。
- 迁移在 WriterActor 启动时、开放写之前跑，事务包裹每个版本步进。
- `oc doctor` 报告当前 `user_version` 与目标版本差异。

### 3.3 Schema（MVP 全表）

```sql
-- ── 会话与转写 ──────────────────────────────────────────────
CREATE TABLE session (
  id            TEXT PRIMARY KEY,          -- 'main' 或子会话 uuid
  kind          TEXT NOT NULL,             -- main|cron|dreaming|lane2
  created_at    INTEGER NOT NULL,          -- unix millis
  reset_at      INTEGER                    -- 最近一次 reset（用于起点定位）
);

CREATE TABLE entry (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id    TEXT NOT NULL REFERENCES session(id),
  seq           INTEGER NOT NULL,          -- 会话内单调序号
  role          TEXT NOT NULL,             -- user|assistant|tool|system
  content       TEXT NOT NULL,             -- JSON: 文本/工具调用/结果的判别联合
  tokens_est    INTEGER NOT NULL,          -- 近似 token（字符/4 或 tiktoken）
  created_at    INTEGER NOT NULL,
  UNIQUE(session_id, seq)
);
CREATE INDEX idx_entry_session_seq ON entry(session_id, seq);

-- ── 记忆索引 + 向量 ─────────────────────────────────────────
CREATE TABLE memory (
  id            TEXT PRIMARY KEY,          -- uuid
  tier          TEXT NOT NULL,             -- curated|episodic|prospective|review
  origin        TEXT NOT NULL,             -- Owner|Agent|Untrusted|System  ★provenance
  text          TEXT NOT NULL,
  keywords      TEXT,                      -- 归一化词法索引（空格分隔）
  importance    REAL NOT NULL DEFAULT 0.5, -- 0..1
  created_at    INTEGER NOT NULL,
  last_used_at  INTEGER,                   -- 用于半衰期
  use_count     INTEGER NOT NULL DEFAULT 0,
  content_hash  TEXT NOT NULL,             -- ★dreaming 乐观并发重校验
  injected_mark INTEGER NOT NULL DEFAULT 0 -- ★召回环防护：注入过则置位，不再被重抽取
);
CREATE INDEX idx_memory_tier_origin ON memory(tier, origin);

-- sqlite-vec 虚表：记忆向量（feature memory-vec，默认开）
CREATE VIRTUAL TABLE memory_vec USING vec0(
  memory_id TEXT PRIMARY KEY,
  embedding FLOAT[768]                     -- 维度随 embedding 模型
);

-- ── 主动性 ─────────────────────────────────────────────────
CREATE TABLE cron (
  id            TEXT PRIMARY KEY,
  expr          TEXT NOT NULL,             -- cron 表达式
  prompt        TEXT NOT NULL,             -- 触发时注入的指令
  tz            TEXT NOT NULL,             -- IANA 时区
  next_at       INTEGER,                   -- 预计算下次触发（server 维护）
  last_fired_at INTEGER,
  enabled       INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE standing_intent (
  id            TEXT PRIMARY KEY,
  text          TEXT NOT NULL,
  keywords      TEXT,                      -- 词法预筛
  trigger_vec   BLOB,                      -- 向量预筛（可空）
  scope         TEXT,
  cooldown_secs INTEGER NOT NULL DEFAULT 86400,   -- anti-nagging，默认 24h
  budget        INTEGER NOT NULL DEFAULT 3,        -- 默认 3 次
  fired_count   INTEGER NOT NULL DEFAULT 0,
  last_fired_at INTEGER,
  expiry_at     INTEGER,                            -- 默认 90 天
  created_at    INTEGER NOT NULL
);

-- ── 后台任务台账 ───────────────────────────────────────────
CREATE TABLE task (
  id            TEXT PRIMARY KEY,
  kind          TEXT NOT NULL,             -- exec_bg|dreaming|cron_run|...
  state         TEXT NOT NULL,             -- queued|running|done|failed|cancelled
  detail        TEXT,                      -- JSON
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

-- ── 审批 / 审计 ────────────────────────────────────────────
CREATE TABLE audit (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  at            INTEGER NOT NULL,
  actor         TEXT NOT NULL,             -- user|agent|system
  action        TEXT NOT NULL,             -- exec_approved|memory_write|config_change|...
  payload       TEXT,                      -- JSON，脱敏
  hash_prev     TEXT,                      -- 可选：链式哈希，防篡改
  hash_self     TEXT
);

-- ── 配置状态（运行时可变部分） ─────────────────────────────
CREATE TABLE kv (
  k TEXT PRIMARY KEY,
  v TEXT NOT NULL                          -- JSON
);
```

### 3.4 关键设计点

- **单库够用**：单用户消灭"共享 DB + per-agent DB"。子会话用 `session.kind` 区分，同库不同行。
- **origin 是列不是推断**：写入端在 `oc-server` 分类后带进 `NewMemory`；store 只存不判。**绝不默认 Owner**（见 §11.2）。
- **向量与文本分离**：`memory` 存元数据 + 文本，`memory_vec` 存向量，用 `memory_id` 关联。Lane1 排名走 `memory` 表 SQL，trigger/Lane2 向量预筛走 `memory_vec`。
- **半衰期在 SQL 里算不了指数**：`rank_search` 只取候选集（按 keywords/importance 粗筛 + limit），**精确排名公式在 oc-core 用取回的字段算**（§4.5）。store 不做浮点排名逻辑，保持"策略在 core"。

## 4. oc-core：领域层

**总原则**：oc-core 是**纯策略的集合**。它不 spawn task、不开连接、不读时钟、不 rand。所有外部量（now、随机、模型输出、DB 查询结果）作为**输入参数**传入，core 输出**决策/计划**（结构体），由 oc-server 执行。这让 core 100% 可确定性单测。

模块：`session / agent / queue / prompt / context / compaction / tool / memory / model / proactive / config`。

### 4.1 session：会话模型

单用户 → 固定"主会话"，外加可创建的隔离子会话。无多 agent、无 DM scope。

```rust
pub struct SessionState {
    pub id: SessionId,
    pub kind: SessionKind,       // Main | Cron | Dreaming | Lane2
    pub turns: TurnCounter,
    pub reset_marker: Option<Seq>, // reset 后，注入/加载从此 seq 起
}

pub enum SessionCmd { Reset, }   // /new /reset：清空活跃上下文，transcript 仍留库
```

`reset` 语义：不删 transcript（可回忆），只把"活跃上下文起点"推进到当前 seq，并触发一次记忆 flush（见 §11）。

### 4.2 agent：循环状态机

Agent loop 是纯状态机：给定当前状态 + 一个"步进事件"，输出下一状态 + 一组"副作用请求"（由 server 执行）。

```rust
pub enum RunState {
    Idle,
    AwaitingModel,        // 已发请求，等 SSE
    Streaming,            // 正在收 assistant delta
    AwaitingTool(ToolCallId),
    AwaitingApproval(ToolCallId),  // exec 审批门
    Compacting,           // 上下文溢出，压缩中
    Terminal(RunOutcome),
}

pub enum RunOutcome {
    Completed,            // 正常结束（模型无更多工具调用）
    Aborted,              // 用户/看门狗/超时中止
    Failed(ErrorKind),
    Panicked,             // catch_unwind 归一
    LoopDetected,         // 打转
}

/// 纯步进：不执行副作用，只返回"要做什么"
pub fn step(state: RunState, ev: StepEvent, ctx: &StepCtx) -> (RunState, Vec<Effect>);

pub enum Effect {
    CallModel(ModelRequest),
    ExecTool(ToolInvocation),
    AskApproval(ToolInvocation),
    EmitAssistant(String),
    EmitLifecycle(LifecyclePhase),
    Compact(CompactPlan),
    PersistEntry(NewEntry),
}
```

**终态归一化**：所有结束路径（正常 / 中止 / 失败 / panic / 打转）都收敛到 `RunOutcome`，server 据此发 `lifecycle` 事件并释放车道。**回复整形**：流式增量在 core 侧做最小规整（去空 delta、合并连续文本），不做渲染（渲染在 TUI）。

### 4.3 queue：队列 + steer/interrupt + 卡死恢复

主会话车道**串行**，队列管理"排队轮 + 插话 + 中止"。

```rust
pub struct RunQueue {
    active: Option<ActiveRun>,       // 当前活跃 run
    pending: VecDeque<QueuedTurn>,   // 有界；满了拒绝并提示
}

pub enum QueueCmd {
    Enqueue(UserTurn),
    Steer(SteerText),        // 插话：注入到活跃 run 的下一步上下文（不新建 run）
    Followup(UserTurn),      // 追加为下一轮
    Collect,                 // 批量取排队项合并
    Interrupt(InterruptKind) // Soft: drain 排队轮; Hard: 立即 abort 活跃 run
}
```

**`chat.abort` 语义分层**（对齐落地方案 M3/M4）：
- **M3 版**：只中止当前活跃 run（供空闲看门狗 / run 超时复用）。
- **M4 完整版**：先 drain 掉排队轮（清 `pending`），再中止活跃 run；对应 `/stop`。

**卡死恢复**：queue 暴露纯判定 `fn diagnose(run: &ActiveRun, now, thresholds) -> RunHealth`（`Healthy | LongRunning | Stalled | Stuck`）。server 的心跳扫描调用它，`Stuck` 且超 abort 阈值 → 触发 `Interrupt(Hard)` 释放车道（详见 §10）。

### 4.4 prompt：系统提示词组装（纯函数）

```rust
/// 确定性组装：相同输入 → 逐字节相同输出（对 prompt cache 至关重要）
pub fn render_system_prompt(inputs: &PromptInputs) -> RenderedPrompt;

pub struct PromptInputs<'a> {
    pub soul: &'a SoulDoc,           // SOUL.md 人格
    pub bootstrap: &'a [MemLine],    // curated tier 注入（有预算）
    pub skills: &'a [SkillDoc],
    pub tools: &'a [ToolSpec],
    pub now: OffsetDateTime,         // 注入的时间也是输入
    pub env: &'a EnvFacts,
}
```

**prompt cache 确定性排序**（落地方案验收项）：所有可变集合（tools、skills、bootstrap 行）在渲染前按**稳定 key 排序**（如 tool name 字典序）；时间戳等易变量集中放在**提示词尾部**或独立不缓存段，让前缀稳定可缓存。此排序逻辑是纯函数，单测锁定输出快照。

### 4.5 memory：纯策略（本层最重）

core 只出**判定与公式**，SQL/向量执行在 store，编排在 server。

**(a) Lane1 排名公式**（延迟敏感，零模型调用）：

```
score(m) = relevance(m, query)         // 词法/向量相似度 0..1
         × halflife(now - m.last_used_at, HALFLIFE=30d)  // 2^(-Δ/HALFLIFE)
         × importance(m)               // 0..1
```

```rust
pub fn rank(cands: &[MemCandidate], q: &Query, now: OffsetDateTime, cfg: &RankCfg) -> Vec<Ranked>;
```

store 负责取候选集（keywords/importance 粗筛 + limit），core 用取回字段算精确 `score` 并排序、截断。

**(b) trigger 注入预筛**：词法或向量相似度 `≥ 0.72`，每轮 `≤ 3` 条，**仅 curated tier** 自动注入。

```rust
pub fn trigger_prefilter(msg: &str, cands: &[MemCandidate], cfg: &TriggerCfg) -> Vec<MemoryId>;
// 返回命中的 curated 记忆 id，供 server 拉全文注入为隐藏上下文
```

**(c) provenance 分类**：写入端调用，**无法判定 → 保守 Untrusted/System**，绝不默认 Owner。

```rust
pub fn classify_origin(src: &WriteSource) -> Origin;
// cron/heartbeat/subagent 会话来源 → 一律非 Owner，且不产生持久候选
```

**(d) Dreaming 双门判定**（纯）：

```rust
/// 门1：确定性排名门（分数/频次/时间窗）
/// 门2：结构排除门（origin ∈ {Untrusted, System} 直接排除）
pub fn dreaming_gate(cands: &[MemCandidate], cfg: &DreamCfg) -> Vec<Consolidation>;
// 通过双门的候选 → 交给"巩固模型轮"重写 MEMORY.md（该轮由 server 发起）
```

**(e) User model supersede**：USER.md 偏好**就地替换**矛盾项，不 append。

```rust
pub fn supersede(existing: &[Pref], incoming: &Pref) -> SupersedePlan; // Replace | Add | Ignore
```

**(f) standing intent 预筛**：每条入站消息确定性预筛（keywords + 向量），命中 → 注入隐藏上下文；同时套 anti-nagging（cooldown/budget/expiry），这部分与 proactive 共用判定（§4.7）。

### 4.6 model：目录 / 别名 / failover

## 5. oc-llm：模型传输

**职责**：Provider trait + OpenAI/Anthropic 兼容实现 + SSE 流 + failover/retry。**只管传输，不管循环编排**（编排在 server 用 core 的状态机）。

```rust
#[async_trait]
pub trait Provider: Send + Sync {
    fn id(&self) -> ProviderId;
    /// 返回一个增量流；调用方负责在 CancellationToken 触发时 drop 它
    async fn stream_chat(
        &self,
        req: ModelRequest,
        cancel: CancellationToken,
    ) -> Result<BoxStream<'static, Result<Delta, ProviderErr>>>;
}

pub enum Delta {
    Text(String),
    ToolCall(ToolCallDelta),   // 增量拼装工具调用
    Usage(Usage),              // token 计量
    Done(FinishReason),
}
```

- **SSE**：手写解析 on `reqwest` 的 `bytes_stream()`（省依赖）。逐行拆 `data:`，累积 JSON。
- **两 provider 差异**归一到统一 `Delta`：OpenAI `chat/completions` 与 Anthropic `messages` 的流格式在各自实现里翻译，对上层透明。
- **failover/retry**：传输层做**幂等重试**（网络抖动、5xx）；跨 provider failover 的**选择**用 core 的 `failover_plan`，server 编排切换。
- **空闲看门狗接入点**：`stream_chat` 每收到一个 Delta 就重置看门狗计时（在 server 侧包裹流做 `tokio::time::timeout` per-delta，见 §10）。
- **cloud vs 自托管**：`ProviderId`/model 能力标注决定看门狗阈值（cloud 120s / 自托管 300s）。

## 6. oc-tools：工具集

**职责**：`exec / process / file / web_fetch / web_search / ask_user / message` + 工具策略管道 + exec 审批门 + 结果净化。

```rust
#[async_trait]
pub trait Tool: Send + Sync {
    fn spec(&self) -> ToolSpec;                    // name/desc/参数 schema（进 prompt）
    fn policy(&self) -> ToolPolicy;                // 是否需审批 / 超时 / 可后台
    async fn invoke(&self, args: Value, cx: ToolCtx) -> Result<ToolOutput>;
}

pub struct ToolCtx {
    pub cancel: CancellationToken,   // 工具级超时/中止
    pub emit: ToolEmitter,           // 流式 update 事件
    pub approval: ApprovalGate,      // exec 用
}
```

### 6.1 工具清单与策略

| 工具 | 说明 | 策略要点 |
|---|---|---|
| `exec` | 跑一次性命令/脚本 | **审批门**（default deny 危险类）；工具级超时；结果净化 |
| `process` | 长命令转后台、可 kill、查状态 | 转 background task 台账；返回 handle |
| `file` | 读/写/列/patch 文件 | 路径白名单；写操作审计 |
| `web_fetch` | 抓 URL → markdown | 出站请求；结果视为 **Untrusted**（provenance） |
| `web_search` | 搜索 | 同上，结果 Untrusted |
| `ask_user` | 主动向用户提问（阻塞 run 等答复） | 经 `proactive`/`tool` 事件推到 client |
| `message` | 主动发消息给用户 | 走事件流 |

### 6.2 exec 审批门

```rust
pub enum ApprovalDecision { Allow, AllowOnce, Deny, AllowAndRemember(Rule) }
pub fn classify_command(cmd: &str, rules: &PolicySet) -> RiskClass; // Safe|NeedsApproval|Blocked
```

- 危险命令（rm -rf、写系统目录、curl|sh 等）→ `NeedsApproval` → server 发 `AskApproval` effect → client 弹审批 → 回执驱动状态机继续。
- 分类是纯函数（core 或 tools 内纯模块），可单测；规则集可配置。

### 6.3 结果净化 + loop detection 接入

- **结果净化**：截断超长输出、剥控制字符、限制注入体积（防上下文爆 + 防注入）。
- **loop detection**：core 侧纯判定 `detect_loop(recent_actions) -> bool`（重复工具调用/相同参数/无进展）；server 在每步后调用，命中 → `RunOutcome::LoopDetected`。

## 7. oc-server：编排层

**职责**：唯一的组装/编排层。持有 tokio runtime、连接管理、EventBus、SessionActor、Scheduler、TaskLedger、IdempotencyCache；把 core 的决策落地为真实副作用。

### 7.1 顶层结构

```rust
pub struct Server {
    core_cfg:  ArcSwap<Config>,       // 代际快照，热更
    catalog:   ArcSwap<ModelCatalog>,
    store:     Arc<dyn Store>,
    providers: Arc<ProviderRegistry>,
    tools:     Arc<ToolRegistry>,
    bus:       broadcast::Sender<Event>,
    session:   SessionActor,          // 主会话车道
    scheduler: Scheduler,             // 心跳 + cron 堆
    ledger:    TaskLedger,
    idem:      DashMap<IdemKey, CachedRes>,
}
```

### 7.2 请求分发

`Dispatcher` 收 `Req` → 校验 → 幂等检查 → 路由到对应 handler → 返回 `Res`。side-effecting 方法（`ChatSend`）立即返回 `{run_id}`，实际处理异步进行，进展经事件流推送。

### 7.3 SessionActor：run 驱动循环

这是 core 状态机的**执行器**：

```
loop {
  ev = next_step_event(active_run).await   // SSE delta / 工具结果 / 审批回执 / 超时
  (new_state, effects) = oc_core::agent::step(state, ev, ctx)  // 纯
  for eff in effects { execute(eff).await } // 真正副作用：调 provider/tool/store/发事件
  state = new_state
  if let Terminal(outcome) = state { finalize(outcome); release_lane(); break }
}
```

每个 run 包 `catch_unwind` + `tokio::time::timeout`（run 超时）+ 空闲看门狗（per-delta timeout）。

### 7.4 Scheduler：心跳 + cron

```rust
pub struct Scheduler {
    heartbeat: Interval,               // M3：固定间隔 tick 底座
    cron_heap: BinaryHeap<NextFire>,   // M6：cron/intent 触发（最小堆按 next_at）
}
```

- **M3**：只有固定间隔 heartbeat tick，触发注册的回调（初期无回调，占位）。
- **M4**：挂"卡死会话扫描器"（调 `queue::diagnose`）。
- **M5**：挂 dreaming 触发器（夜间/空闲，调 `dreaming_gate`）。
- **M6**：接入 cron 最小堆 + anti-nagging；触发 → 起隔离子会话跑一轮 → 结果经 `proactive` 事件推送。

调度回调**各自套 `tokio::time::timeout` + fallback**：记忆/dreaming 失败绝不阻塞主会话（落地方案 §4 硬约束）。

### 7.5 TaskLedger：后台任务台账

- 每个后台任务（`process` 长命令、dreaming、cron run）落 `task` 表 + 内存视图。
- 状态变更经 `Task(update)` 事件推送。
- **崩溃恢复**：重启时扫 `task` 表 `running` 记录，标记为中断并（可选）续跑；已完成但未 push 的结果在下条消息时补推（对齐 M4/M5 验收）。

### 7.6 EventBus

- `tokio::sync::broadcast`，每 client 独立订阅。
- 慢 client `Lagged` → 提示重连/重新 `Status` 拉快照。**永不阻塞 run**。

## 8. oc-tui

**职责**：协议的第一个 client。`ratatui` + `crossterm`。

- 连上 socket → `Connect` → 收 `Hello{snapshot}` 渲染初始状态。
- 输入框发 `ChatSend`；`Esc`/`/stop` 发 `ChatAbort`。

- 布局：消息流区 + 输入区 + 状态栏（当前 run 状态 / 后台任务数 / 连接状态）。
- **纯展示**：不含业务逻辑；所有决策在 daemon。断线自动重连 + 重新 `Status` 拉全量。

## 10. 防卡死：阈值与机制汇总

集中定义（其它章节引用不重复）。默认值可配。

### 10.1 阈值表

| 参数 | 默认 | 说明 | 里程碑 |
|---|---|---|---|
| 空闲看门狗（cloud） | 120s | 两个 delta 间最大间隔，超则判模型不吐 token | M3 |
| 空闲看门狗（自托管） | 300s | 同上，自托管更宽松 | M3 |
| run 超时 | 长（可配，0=无限） | 单 run 墙钟上限 | M3 |
| 工具级超时 | 每工具在 policy 里定义 | 工具卡住 | M4 |
| loop detection 窗口 | 最近 N 步 | 重复动作/无进展判定 | M4 |
| 卡死 abort 阈值 | **≥5min 且 ≥3× 警告阈值** | 达到才 abort，避免误杀慢 run | M4 |

**慢 ≠ 卡**：abort 阈值同时满足"≥5min"和"≥3× 警告阈值"才触发；未达阈值的慢 run 保持 `LongRunning` 不误杀。

### 10.2 七种死法 → 机制

| 死法 | 机制 | 落点 |
|---|---|---|
| 模型不吐 token | 空闲看门狗（per-delta timeout） | server 包 provider 流 |
| run 跑太久 | run 超时 + abort timer | server run task |
| 工具卡住 | 工具级超时 + `process` 转后台/可 kill | tools policy + server |
| 模型打转 | loop detection | core 判定 + server 调用 |
| 上下文爆 | 压缩 + overflow→压缩重试 + 结果剪枝 | core compaction + server |
| 车道被占死 | 卡死诊断（`diagnose`）+ abort-drain 释放车道 | core queue + scheduler 扫描 |
| 用户要打断 | `chat.abort`（M4: 先 drain 排队轮再中止活跃 run）+ `/stop` | proto + server queue |
| 崩溃/重启 | transcript 落库续接 + task 台账补 push | store + ledger |

### 10.3 panic 隔离

- profile `panic="unwind"`（落地方案 §7）。
- run 主体 `catch_unwind` → panic 归一为 `RunOutcome::Panicked` → `lifecycle(error)` → 释放车道。**进程存活**。
- 工具 panic 同样被 run 边界捕获，转为该 run 错误终态。
- 验收（M4）：单工具 panic 不杀进程。

## 11. 记忆系统端到端时序

### 11.1 入站消息的记忆处理（Lane1，延迟敏感，零模型调用）

```
用户消息到达 (SessionActor)
  │
  ├─ [并行、各套 timeout+fallback，失败不阻塞回复]
  │   ├─ store.rank_search(粗筛候选) ─► core::memory::rank(now) ─► 取 top
  │   ├─ core::memory::trigger_prefilter(msg, cands) ─► 命中 curated (≥0.72, ≤3)
  │   └─ core::memory::intent_prefilter(msg) + proactive::allow_fire ─► 命中 intent
  │
  ├─ 注入：仅 curated tier 自动注入为隐藏上下文；命中的注入项置 injected_mark（防召回环重抽取）
  │
  └─► 组装 prompt (core::prompt::render) ─► 正常 agent 轮
```

Lane1 全程**无模型调用**，每步 `tokio::time::timeout` 包裹，超时/失败则跳过该步继续回复。

### 11.2 provenance 分类（抗投毒）

```
写记忆候选来源:
  用户显式 "记住…"        → Owner
  主会话 agent 推断        → Agent
  web_fetch/web_search 结果 → Untrusted
  cron/heartbeat/subagent  → 不产生持久候选（且即便产生也非 Owner）
  无法判定                  → Untrusted/System（保守）
```

**绝不默认 Owner**。分类在 core（`classify_origin`，纯），origin 作为列存入。dreaming 门2 结构性排除 `Untrusted/System`。

### 11.3 Lane2（升级检索，跨会话回忆）

```
仅当 [显式召回意图] 且 [Lane1 无强命中]:
  server 起隔离子会话 (SessionKind::Lane2)
    │
    ├─ core 出检索策略 (查哪些 tier / 向量 or 词法 / k)
    ├─ store 执行 vec_search + 跨 session transcript 检索
    └─ 子会话综合 ─► 结果回注主会话 (作为 Agent-origin 上下文, 不自动持久化为 Owner)
```

### 11.4 Dreaming（后台巩固，M5，挂 M3 心跳 tick）

```
心跳 tick (夜间/空闲) 触发:
  light/REM: 暂存反思 (episodic)
  deep:
    ├─ 门1: core::dreaming_gate 确定性排名门 (分数/频次/时间窗)
    ├─ 门2: 结构排除 origin ∈ {Untrusted, System}
    ├─ 双门通过 ─► 巩固模型轮重写 MEMORY.md
    └─ 写安全: 乐观并发
          读 content_hash ─► 生成新内容 ─► 重校验 hash 未变 ─► 原子 rename
          hash 变了 (并发写) ─► 回退 append-only, 不覆盖
```

dreaming 判定纯在 core（可单测），文件/DB 读写在 store，调度在 server。**失败绝不阻塞主会话**。

### 11.5 会话 reset / 压缩前的记忆 flush

`session.reset` 或压缩触发前，先把当前会话中"值得记住"的内容 flush 为 episodic 候选（不丢），再推进上下文起点 / 压缩。

## 12. 主动性端到端时序

### 12.1 调度底座演进（对齐里程碑）

```
M3: Scheduler 只有固定间隔 heartbeat tick (占位回调)
M4: 挂 卡死会话扫描器 (queue::diagnose ─► abort-drain)
M5: 挂 dreaming 触发器 (dreaming_gate)
M6: 接入 cron 最小堆 + anti-nagging，统一纳入 proactive 管理
```

### 12.2 cron 触发（M6）

```
Scheduler.cron_heap 到期 (next_at ≤ now):
  ├─ proactive::allow_fire 检查 (cooldown/budget/expiry) ─ 拒 → 跳过 + 重排
  ├─ 起隔离子会话 (SessionKind::Cron)，own timer + 到期 abort + 清理
  ├─ 跑一轮 agent (注入 cron.prompt)
  ├─ 结果 ─► Event::Proactive{kind: Reminder} ─► 所有 client
  └─ 更新 last_fired_at / fired_count；core::next_fire 算下次 ─► 重排堆
```

### 12.3 standing intent 触发

```
每条入站消息:
  core::intent_prefilter (keywords + 向量) 命中
    ─► proactive::allow_fire (anti-nagging)
        ─► 允许: 注入隐藏上下文 (提醒 agent 该待办) + fired_count++
        ─► 拒绝: 静默跳过
时间型待办 → 编译成 cron (进 cron 表)
```

### 12.4 wake

立即或下次心跳注入唤醒文本 → 驱动一轮主动 agent。

### 12.5 anti-nagging 默认（§4.7 引用）

cooldown 24h / budget 3 次 / 90 天过期 / ≤3 条每轮。全部可配，判定在 `proactive::allow_fire`（纯）。

### 13.2 config.toml 骨架

```toml
proto_version = 1

[server]
transport = "unix"          # unix | pipe | ws
# ws.token = { file = "..." }  # ws-remote feature

[[models]]
alias = "default"
provider = "anthropic"       # openai | anthropic
model = "claude-..."
hosting = "cloud"            # cloud | self  → 决定看门狗阈值
api_key = { env = "ANTHROPIC_API_KEY" }   # SecretRef: inline|env|file

[memory]
vec = true                   # memory-vec feature
halflife_days = 30
trigger_threshold = 0.72
trigger_max_per_turn = 3

[proactive]
heartbeat_secs = 60          # 心跳 tick 间隔
intent_cooldown_secs = 86400
intent_budget = 3
intent_expiry_days = 90

[tools]
exec_timeout_secs = 120
[tools.approval]
mode = "prompt"              # prompt | allow | deny 危险类

[watchdog]
idle_cloud_secs = 120
idle_self_secs = 300
run_timeout_secs = 0         # 0 = 无限
abort_min_secs = 300         # 卡死 abort 下限
```

### 13.3 SecretRef 与热更

- `SecretRef` 三态 `inline|env|file`；解引用是 IO，在 server 做，core 只持类型。
- 每配置项标注 `ReloadKind`：`Hot`（如 trigger_threshold、anti-nagging）走 `ArcSwap` 热更；`RestartRequired`（如 transport、db 路径）提示重启。

| 层 | 方法 | 重点 |
|---|---|---|
| oc-core（纯） | 单元 + 属性测试（`proptest`） | 排名公式单调性、trigger 阈值边界、dreaming 双门、anti-nagging 状态机、prompt 确定性快照、cron next_fire、loop detection |

## 16. 开放问题

1. **embedding 来源**：向量记忆需要 embedding。走 provider 的 embedding API（联网、成本）还是本地小模型？维度（schema 中 `FLOAT[768]`）需据此定。→ 建议 M5 前定；MVP 可先用 provider embedding，本地化留 Phase 2。
2. **tokenizer 精度**：默认"字符/4"近似，`tiktoken` 为可选 feature。压缩/预算的边界误差是否可接受？→ 先近似，压缩误杀多了再开 feature。
3. **Windows 命名管道权限模型**：与 unix socket 0600 语义不完全对等，需确认单用户隔离足够。→ M2 双平台验收时确认。
4. **dreaming 巩固模型轮的成本**：夜间跑重写 MEMORY.md 会消耗 token。是否设每日预算上限？→ 纳入 anti-nagging 类预算，M5 定默认值。
5. **审批规则的可学习性**：`AllowAndRemember` 落规则集，规则冲突/撤销的 UX。→ M4 细化。
6. **引用文档缺失**：落地方案引用的 `02-核心机制.md`、`03-Rust落地方案.md` 当前仓库不存在。本设计以 01 为唯一权威源；若后续补入机制文档，需回归核对记忆/压缩机制细节是否一致。
