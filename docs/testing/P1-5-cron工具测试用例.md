# 12 — P1-5 cron 工具运行时测试用例

> 编写日期：2026-09-01。对应改动：P1-5「cron 工具暴露 + 系统提示引导」（见
> [下一阶段计划](../plan/下一阶段计划.md) P1-5 条目）。
> 目的：验证模型在遇到定时/延时提醒需求时，能正确使用 `cron_add` 工具而非退化到
> shell 阻塞等待（`Start-Sleep` / `sleep` / `timeout`）。
> 自动化回归：无（需真实模型决策 + 系统提示响应）。本文覆盖「真机跑起来」才能
> 观察到的端到端交互与模型工具选择行为。

## 背景：P1-5 解决什么问题

**现象（2026-08-31 真机暴露）**：用户说「12:50 提醒我喝水」，模型**不用已有的 cron 能力**，
而是想在一次 run 内**同步阻塞等到 12:50**——反复调 `sys:now` 查时间 +
`powershell Start-Sleep` / `timeout /T` 硬凑「等待」，6 轮工具调用约 76 秒后触发
loop detection、判 `LoopDetected` 中止，提醒没设成。

**根因（两层）**：
1. **能力认知缺失**：cron 定时任务能力已实现（[proactive.rs](../../crates/oc-server/src/proactive.rs) + `cron.add`），
   但模型不知道该用它、也没有可直接调用的 cron 工具，于是选了「run 内干等」这条错路。
2. **shell 等待不可靠**：PowerShell `Start-Sleep` 在测试机上「只回显不执行」，
   模型反复换命令试 → 撞 loop detection。此故障是①的次生，①修好后该路径不会被触发。

**修法**：
- **主**：把 cron 引导进模型决策——系统提示明确「定时/延时/未来某时刻的提醒用 cron，
  不要用 shell 睡眠阻塞等待」；并把 `cron.add` 暴露为模型可直接调用的工具（此前仅 CLI/proto）。
- **副**：给模型一个可靠的「延时/定时」原语，替代拿 shell 硬凑。

## TC-P1-5a — 绝对时间提醒 → 调 cron_add ⭐（核心用例）

**验证**：用户说「X 点 Y 分提醒我做 Z」，模型应**立即调 `cron_add` 工具**设置定时任务，
而非在 run 内阻塞等待。

**步骤**：
1. TUI 里说一个**未来几分钟**的时间点（避免等太久），例如：
   > 12:50 提醒我喝水
   或（相对表述）：
   > 5 分钟后提醒我站起来活动一下
2. 观察模型的**第一个工具调用**是否是 `cron_add`（而非 `sys:now` / `exec`）。
3. 观察模型回复是否即时反馈「已设置提醒」（而非「正在等待…」）。

**通过标准**：
- 模型**第一轮就调** `cron_add`，参数包含正确的 cron 表达式（或相对延时秒数）+ prompt 内容。
- 回复立即返回，**不阻塞 run**（TUI 可继续发其他消息）。
- daemon 日志可见 `cron：新增任务 <id>`、`已排入调度`。
- `oc cron list` 能看到刚建的任务。

**失败特征**：
- 模型调 `sys:now` 查时间、或调 `exec` 执行 `Start-Sleep` / `sleep` / `timeout` ← **这是退化行为**。
- run 长时间无响应（卡在等待循环）。
- 触发 loop detection 中止。

## TC-P1-5b — 相对延时提醒 → 调 cron_add

**验证**：用户说「N 分钟后 / N 小时后提醒我」，模型能正确转换为 cron 延时任务。

**步骤**：
1. TUI 里说：
   > 10 分钟后提醒我查看日志
2. 观察工具调用与回复（同 TC-P1-5a）。

**通过标准**：
- 模型调 `cron_add`，参数是相对延时（如 `delay_secs: 600`）或对应的 cron 表达式。
- 立即反馈，不阻塞。

---

## TC-P1-5c — 定期重复提醒 → 调 cron_add

**验证**：用户说「每天 X 点提醒我 Y」，模型能正确创建重复任务。

**步骤**：
1. TUI 里说：
   > 每天下午 3 点提醒我喝水
2. 观察工具调用。

**通过标准**：
- 模型调 `cron_add`，cron 表达式带 `* * *`（每天）+ 正确的小时/分钟。
- `oc cron list` 可见任务，无 `expiry_at`（长期有效）。

---

## TC-P1-5d — cron 任务成功创建并触发 ⭐

**验证**：通过 TC-a/b/c 创建的任务，到时间后真的触发并发消息。

**步骤**：
1. 按 TC-P1-5a 创建一个**1-2 分钟后**触发的任务（避免等太久）。
2. 等到触发时间，观察 TUI 是否收到**新消息**（proactive 主动发起的对话）。

**通过标准**：
- TUI 在预定时间收到一条新消息，内容是 cron 任务的 prompt（如「提醒：喝水」）。
- daemon 日志可见 `proactive：触发定时任务 <id>`。
- `oc cron list` 显示该任务的 `last_run` 更新为触发时间。

**失败特征**：
- 到时间了但没消息（任务没触发 / 消息没发出）。
- 触发了但 TUI 收不到（事件通道问题，属 P0 回归）。

## TC-P1-5e — 不应退化到 shell 睡眠 🔴（防回归）

**验证**：确认模型**不再**走 shell 阻塞等待这条错路。

**步骤**：
1. 按 TC-P1-5a 说一个定时提醒。
2. **在模型回复前**，tail 日志看工具调用序列：
   ```bash
   tail -f "$OC_HOME/logs/oc.log.$(date +%Y-%m-%d)" | grep -E "tool_call|exec"
   ```

**通过标准**：
- 日志里**没有** `exec` 调用 `Start-Sleep` / `sleep` / `timeout` / `ping -n`（Windows 上常见的延时 hack）。
- 日志里**没有**连续多次 `sys:now` 查时间（轮询等待的特征）。
- 只有一次 `cron_add` 调用，然后 run 结束。

**失败特征**：
- 日志出现 `exec: Start-Sleep` / `exec: sleep` / `exec: timeout` ← **说明修法没生效**，
  模型没听系统提示、仍在拼 shell。
- 连续 3+ 次 `sys:now` ← 模型在轮询等时间到，说明它不知道 cron 能力。

**修复方向（若失败）**：
- 检查系统提示词是否真的注入了 cron 引导（[prompt.rs](../../crates/oc-core/src/prompt.rs) 第 82-90 行）。
- 检查 `cron_add` 工具是否真的注册到 registry（[lib.rs](../../crates/oc-server/src/lib.rs)）。
- 可能需要加强提示词措辞、或在工具描述里明确「用于定时/延时提醒」。

## 已知限制（不是 bug）

1. **cron 表达式精度**：模型生成的 cron 可能不够精确（如「5 分钟后」可能只精确到分钟边界）——
   这是模型决策问题，不属工具能力缺陷。
2. **相对延时的绝对化**：`cron_add` 内部会把「10 分钟后」转成绝对 cron 表达式（具体分钟数），
   而非真正的「from now」语义——当前实现合理，因 cron 本身是绝对时间调度。
3. **时区**：cron 表达式用本地时间，跨时区场景未测（个人助手假设单时区）。
