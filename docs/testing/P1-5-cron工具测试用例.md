## 背景：为什么这份用例要盯着「时区」和「有没有响」

首版只做了「暴露 `cron_add` + 提示引导」，真机复测的结果值得记住：

**模型确实改用工具了**（不再拼 shell、不再撞 loop detection，首版目标达成），
**但提醒一次都没响**。三个缺陷叠在一起：

1. **时区没落地**：本地 21:46 的提醒被排到次日 05:46（差 8 小时）。表达式一律按 UTC
   解释，`tz` 列自 M6 起存了没人读。
2. **模型没有自查手段**：用户说「没收到」，模型只能猜——猜成「本环境 cron 送不到」，
   然后改用更不可靠的替代方案，反复道歉。
3. **亚分钟延时表达不了**：用户要「90 秒后」，模型只能写成 `46 21 * * *`，白得一条
   **每天**都响的任务。

所以下面的用例里，**TC-a（时区）和 TC-d（真的响了）是最重要的两条**——首版正是在
这两点上"看起来成功、实际没用"。

## TC-P1-5a — 定时提醒在本地正确时刻触发 ⭐

**验证**：模型建的任务，`next_at` 落在**用户所在时区**的正确墙上时间。

**步骤**：
1. 记下当前本地时间，选一个 **2~3 分钟后**的时刻。
2. TUI 里说（用绝对时间，逼模型走 `op=add` 的表达式路径）：
   > 今天 HH:MM 提醒我喝水    ← 填上一步选的时刻
3. 立刻在另一个终端核对：
   ```bash
   oc cron list
   ```

**通过标准**：
- `oc cron list` 的「下次」列显示的是**本地墙上时间**且**等于你要求的时刻**，
  后面括号里是本机时区名，例如：
  ```
  cron-01a0…  [启用]  46 21 * * *  下次:2026-09-01 21:46 [Asia/Shanghai]  «提醒喝水»
  ```
- 模型的回复里也复述了这个本地时间（不是 unix 秒）。

**失败特征（首版就是这样）**：
- 「下次」显示的日期是**明天**，或时刻与你要求的差了整数小时 → 时区没生效。
  东八区会差 8 小时，即要求 21:46 却排到次日 05:46。
- 显示 `unix 1788…` → 时区名无法解析（见下方排查）。

**排查**：
```bash
# daemon 启动日志里应无时区告警；若有则时区探测失败、已退回 UTC
grep -i "无法探测本机时区" "$OC_HOME/logs/oc.log.$(date +%Y-%m-%d)"
```

## TC-P1-5b — 亚分钟延时秒级准确 ⭐

**验证**：「N 秒后」走 `op=delay`，精确到秒，不被舍进整分钟。

**步骤**：
1. TUI 里说：
   > 10 秒后提醒我
2. 掐表等待。

**通过标准**：
- 约 10 秒（±3 秒）后 TUI 出现提醒。
- 日志可见 `proactive：一次性延时任务已创建 secs=10`。
- 模型**没有**说「cron 最小粒度是分钟，做不到」之类的话——那是首版的行为。

**失败特征**：
- 等了将近一分钟才响 → 精确 timer 没挂上，落到心跳扫描兜底了。
- 模型改用 `op=add` 凑一个分钟级表达式 → 工具描述没让它选对 op。

---

## TC-P1-5c — 模型能自查已设任务 ⭐

**验证**：模型用 `op=list` 查证，而不是凭猜测答复。

**步骤**：
1. 先按 TC-a 设一条 3 分钟后的提醒。
2. **在触发前**问模型：
   > 我刚才设的提醒还在吗？什么时候响？

**通过标准**：
- 模型调 `cron` 工具（`op=list`），然后答出**具体的本地时间和剩余时长**。
- 答案与 `oc cron list` 一致。

**失败特征**：
- 模型不查就答（"应该还在吧"）。
- 模型说自己没有查询任务的能力 ← 首版的行为。

---

## TC-P1-5d — 到点消息真的推到 TUI ⭐

**验证**：整条链闭合——排期正确 + 心跳/timer 触发 + 事件推到 client。

**步骤**：
1. 按 TC-a 设一条 2 分钟后的提醒。
2. **什么都别做**，等到点（不要在 TUI 里继续聊，避免混淆）。

**通过标准**：
- 到点时 TUI 自行出现一条提醒消息（无需你发任何东西）。
- 日志顺序可见：`proactive：本轮 cron 触发完成` 或精确 timer 路径的触发记录。

**失败特征**：
- 到点无声。先看 `oc cron list`：
  - 「下次」还在未来 → 排期错了，回 TC-a 查时区。
  - 任务已消失但没收到消息 → 触发了但事件没推到 client（属 P0 事件流问题，不是 P1-5）。

---

## TC-P1-5e — 一次性提醒不会次日重复（防回归）

**验证**：`op=delay` 建的任务触发后**被删除**，不会变成每日提醒。

**步骤**：
1. 按 TC-b 设一条 10 秒后的提醒，等它响。
2. 立刻核对：
   ```bash
   oc cron list
   ```

**通过标准**：
- 该任务**已不在列表里**（触发即删）。
- 次日同一时刻不会再响。

**失败特征**：任务还在且「下次」被排到了明天 ← 首版把「90 秒后」写成
`46 21 * * *` 就是这个后果，用户白得一条每天都响的任务。

---

## TC-P1-5f — 不退化到 shell 睡眠（防回归）

**验证**：模型不再拿 shell 硬等。

**步骤**：说一个定时提醒的同时 tail 日志：
```bash
tail -f "$OC_HOME/logs/oc.log.$(date +%Y-%m-%d)" | grep -E "执行工具"
```

**通过标准**：
- 只见 `tool=cron`，**没有** `tool=exec`（Start-Sleep / sleep / timeout / ping）。
- **没有**连续多次 `tool=sys`（轮询查时间的特征）。
- 模型答完即结束本轮，不挂着等。

> 说明：模型查一次 `sys:now` 来把「10 秒后」换算成时刻是**正常**的，
> 连续查三次以上才是轮询等待。

---

## TC-P1-5g — 模型能删除任务

**步骤**：设一条提醒后说「取消刚才那个提醒」。

**通过标准**：模型先 `op=list` 拿 id、再 `op=rm` 删除，然后确认；`oc cron list` 里确已消失。

**失败特征**：模型声称已取消但任务还在（`rm` 删不到时会明确回「没有这条」，
模型不该把它当成功）。

---

## 附：最小验证序列（约 5 分钟）

```bash
# ① 时区（首版失败点）：说「今天 HH:MM 提醒我喝水」（2 分钟后），立刻
oc cron list        # 「下次」须是本地正确时刻 + 本机时区名，不是明天

# ② 亚分钟：说「10 秒后提醒我」——掐表，约 10 秒响

# ③ 到点真响 + 用后即删：等 ① 触发
oc cron list        # 一次性任务应已消失
```

三条都过，P1-5 即算真机通过。
