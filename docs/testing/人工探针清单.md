## 准备

```sh
export RUST_LOG=oc=debug,oc_server=debug
cargo build --release
cargo run --release -- serve      # 终端 A
cargo run --release               # 终端 B（TUI）
```

用默认 `~/.oc`（开发环境无需隔离）。日志落 `~/.oc/logs/oc.log.YYYY-MM-DD`。
需要与自己正跑的 daemon 隔开时设 `OC_SOCKET`（见 [环境陷阱](README.md#环境陷阱)）。

真实模型是本文的前提——这几条要看的正是模型输出质量，mock 无意义。

## P-1 dreaming 重写 MEMORY.md 有无编造 ⭐

原 TC-P1-4h。夜间无人监督的重写若掺入幻觉，会污染此后每轮注入的 curated 核心，
是所有人工项里后果最重的一条。

**做法**：攒够候选后触发一轮 dreaming（调小 `DREAM_EVERY_TICKS` 或等自然触发），
把重写前后的 `~/.oc/soul/MEMORY.md` 逐条对读。

**看什么**：
- 每一条是否都能在原文或对话历史里找到出处，没有"看起来合理但没人说过"的内容
- 合并同主题时语义有没有被改变（"我用 VS Code" + "改用 Neovim" 应体现替换关系，
  而非并列两条矛盾事实）
- 用户手写的段落是否被保留

自动化已覆盖的部分（不必人工重复）：文件不被清空、并发修改退化追加、
无候选不碰文件、不留 `.tmp` —— 见 `dreaming_memory_md.rs`。

## P-2 TUI 错误分支渲染 ⭐

原 TC-H5。错误路径的显示只有人眼能判断是否可理解。

**做法**：让 HTTP 网关与 TUI 抢同一条车道（`bash scripts/h3-concurrent.sh 20 main`
打满队列，同时在 TUI 发消息），观察 TUI 的错误提示。

**看什么**：
- 错误提示是否说清了"发生什么、该怎么办"，而非糊一句 `internal error`
- 状态栏能否回到可用态，不残留"思考中…"
- 长错误文本换行、窗口缩放后有无残影

## P-3 回复自然度与人格一致性

原 TC-P1-2b 的主观部分、TC-1 的观感部分。

**看什么**：
- standing intent 命中时，提醒是**自然地融入回复**，还是像机械插播
- 长回复流式蹦字的节奏是否顺畅（内容完整性已由自动化逐字断言）
- 多轮后人格是否稳定，SOUL.md 的设定有没有漂移

## P-4 首次上手体验

`oc onboard` 全流程走一遍，注意提示语是否清楚、默认值是否合理、
出错时是否给了下一步动作。这条无法自动化，但每次改 onboard 都该走一次。
