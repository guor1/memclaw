# 07 — P0 运行时测试用例

> 编写日期：2026-08-31。对应改动：commit `cbabe7c`「P0 稳定核心闭环」。
> 目的：给出**手动启动 daemon + TUI/CLI** 后，逐项验证 P0-1~P0-4 的可操作步骤。
> 自动化回归见 `crates/oc-server/tests/{long_reply,approval_cancel,antistuck,toolloop}.rs`；
> 本文覆盖的是「真机跑起来」才能观察到的端到端行为。

## 0. 环境准备（一次性）

### 0.1 目录与配置
daemon 根目录默认 `~/.oc/`（Windows: `C:\Users\<你>\.oc\`）。可用环境变量 `OC_HOME`
指向一个**隔离的测试目录**，避免污染日常数据：

```sh
# Git Bash / PowerShell 均可，先导出隔离根目录
export OC_HOME=/c/dev/workspace/MyClaw/.octest      # Git Bash
# $env:OC_HOME = "C:\dev\workspace\MyClaw\.octest"  # PowerShell
```

首次可跑 `oc onboard` 生成骨架，或手动把 `config.example.toml` 复制到 `$OC_HOME/config.toml`。

### 0.2 两种 provider 模式

- **真实模型**（验证流式/长回复最真实）：按 `config.example.toml` 配 DeepSeek，
  设 `DEEPSEEK_API_KEY` 环境变量。
- **审批相关用例**：把 `[tools.approval] mode` 设为 `prompt`（默认即是）。

### 0.3 构建与启动

```sh
cargo build --release                 # 或 debug
# 终端 A：启动 daemon（前台，看 stderr 日志）
cargo run --release -- serve
# 终端 B：进 TUI（无子命令即 TUI）
cargo run --release
```

日志同时落盘 `$OC_HOME/logs/oc.log.YYYY-MM-DD`，排障时 `tail -f` 它。
提高日志级别可见更多细节：

```sh
export RUST_LOG=oc=debug,oc_server=debug,oc_llm=debug
```

> 关键排障抓手：`oc debug`（诊断快照）、`oc debug --watch`（每秒刷新）、
> daemon 日志里的 `事件订阅滞后`（若还出现说明仍有丢帧）、`构建模型请求 shape=...`（每轮消息形状）。

## TC-1 — P0-1：长回复不截断 🔴（最重要）

**验证**：run 内联事件改走 per-run 背压 sink 后，长回复完整送达 TUI，不再中途「塌一段」。

**步骤**：
1. 终端 A 启动 daemon，终端 B 进 TUI。
2. 在 TUI 输入一个会产生**长回复**的问题，例如：
   > 请分 30 条详细列出 Rust 异步编程的最佳实践，每条配一段说明和代码示例。
3. 观察回复流式蹦字直到结束（状态栏从「助手思考中…」回到「已连接」）。

**通过标准**：
- 回复从头到尾连贯，无「跳过一段/半句接后文」的断裂。
- daemon 日志（`RUST_LOG=...=debug`）**不出现** `事件订阅滞后`（Lagged）。
- 用 `/compact` 或重连后拉历史，内容与刚才屏幕所见一致（不再是「屏幕缺、库里全」）。

**失败特征（回归前的旧 bug）**：长回复中途缺一段；日志有 `dropped=N 事件订阅滞后`。

## TC-2 — P0-1：慢消费下背压不丢字

**验证**：客户端消费慢时是「整条流一起变慢」（背压），而非丢中间段。

**步骤**：
1. 触发一个长回复（同 TC-1）。
2. 回复流式输出**期间**，制造消费变慢：在 TUI 里快速连续按 `PageUp`/`PageDown`
   翻动消息区（渲染占用），或把终端窗口频繁改小/滚动。
3. 等回复结束。

**通过标准**：回复可能**变慢**（蹦字节奏被拖），但内容**完整无缺**。日志无 Lagged。

> 原理：`RunSink::Conn` 出站队列满 → `send().await` 挂起 → provider 停止被拉取 →
> 慢，但不丢。见 [sink.rs](../../crates/oc-server/src/sink.rs)。

## TC-3 — P0-2：abort 能打断正在等待的审批 🟠

**验证**：run 卡在审批等待时，`/stop`（abort）能立即释放车道，不再假死。

**步骤**：
1. 确保 `[tools.approval] mode = "prompt"`，daemon 用**带工具**配置启动。
2. TUI 输入一个会让模型调用危险命令的请求，例如：
   > 用 exec 执行 `sudo echo hi`（或 `rm -rf /tmp/xxx`）
3. TUI 弹出审批提示：`批准执行？(y/n)`，状态栏「等待审批」。
4. **既不按 y 也不按 n**，改为发送 `/stop`。
   （若审批模式独占输入，先按一次 `n` 之外的方式无法插入 —— 见下「注意」。）

**通过标准**：
- `/stop` 后 run 立即以错误终态结束，状态栏恢复「已连接」，车道释放。
- 紧接着发一条普通消息能正常得到回复（车道确实空了）。
- daemon 日志可见该 run 以 `Aborted` 终态收尾，无「卡在 gate.ask」迹象。

> **注意**：当前 TUI 在审批态只接受 `y/n`（见 [app.rs](../../crates/oc-tui/src/app.rs) `on_key`）。
> 若无法在审批态发 `/stop`，改用**第二个客户端**验证 server 侧取消：
> 终端 C 跑 `oc debug` 确认有活跃 run 卡在审批 → 用 `oc`（另开 TUI，同会话）发 `/stop`，
> 或直接 kill TUI 触发断连（见 TC-7）。核心是验证 **server 侧 abort/断连能解除审批等待**，
> 自动化已由 `approval_cancel.rs` 覆盖；本用例是真机确认。

## TC-4 — P0-2：卡死看门狗自动释放车道

**验证**：模型长时间无响应时，空闲看门狗/卡死诊断自动中止 run。

**步骤**：
1. 制造「模型迟迟不吐字」：最简单是断网后发消息（provider 建流或首 delta 超时），
   或把 `[watchdog] idle_cloud_secs` 调小（如 5）后发一个会等待的请求。
2. `oc debug --watch` 观察该会话 phase 停在 `awaiting-mdl`，`age` 增长。

**通过标准**：超过 idle 阈值后，run 自动以超时错误终态结束，车道释放；
`oc debug` 中该会话回到 `idle`。

## TC-4b — 审批放行仍正常工作（回归）

**步骤**：同 TC-3 触发审批，这次按 `y` 放行。

**通过标准**：命令执行、结果回喂模型、得到最终回复；`oc debug` 显示 run 正常完成。

---

## TC-5 — P0-3：审批 registry 不泄漏 🟠

**验证**：审批被超时/abort/拒绝后，待处理审批表不残留 entry（长期运行不单调增长）。

**步骤**：
1. `prompt` 审批模式启动。
2. 反复多次触发审批并**中止/拒绝**（重复 TC-3 的 abort 路径，或每次按 `n` 拒绝）5~10 次。
3. 每轮之间跑 `oc debug`，观察是否有异常累积。

**通过标准**：
- 每次审批解决（放行/拒绝/中止/超时）后，该 approval 都被清理。
- 长时间反复操作后，daemon 内存无因审批表持续增长（可选：长跑后看进程内存平稳）。

> 原理：`ApprovalGuard` RAII 在所有退出路径 drop 时清理 registry，见
> [tools_bridge.rs](../../crates/oc-server/src/tools_bridge.rs)。自动化由 `approval_cancel.rs` 断言
> `registry.is_empty()`。

## TC-6 — P0-4：大目录 grep 不冻结其它会话 🟠

**验证**：一个会话对大目录 grep 时，同步遍历不再霸占 tokio worker，其它会话仍可响应。

**步骤**：
1. 准备一个**很大的目录**（如整个 `target/` 或一个大型仓库）。
2. TUI 会话 A（`/session a`）发：
   > 用 file 工具 grep 在 `C:\大目录` 里搜 `TODO`
3. **趁 grep 还在跑**，切到会话 B（`/session b`）发一句普通问候。

**通过标准**：
- 会话 B 能**立即**开始得到回复，不被会话 A 的 grep 阻塞。
- 若 grep 超过工具级 30s 超时，会话 A 得到「工具超时」而非整个 daemon 冻结。

> 原理：`grep`/`glob` 包 `spawn_blocking`，见 [file.rs](../../crates/oc-tools/src/file.rs)。

## TC-7 — 断连不锁车道（sink 断连收敛）

**验证**：TUI 在回复途中断开，run 能感知 sink 不可达并自行收敛，车道不被死连接锁住。

**步骤**：
1. TUI 触发一个长回复（同 TC-1）。
2. 回复途中直接**关闭 TUI 进程**（Ctrl-C 退出 TUI，不是 `/stop`）。
3. 重新 `oc` 进 TUI，或跑 `oc debug`。

**通过标准**：
- daemon 不报错崩溃；`oc debug` 显示该会话最终回到 `idle`（run 已收敛，未卡住占道）。
- 重连后能正常发消息、正常回复。

> 原理：`RunSink::Conn` 的 `send` 返回下游不可达时，driver 触发 `cancel` 收敛 run，
> 见 [run.rs](../../crates/oc-server/src/run.rs) `emit_inline`。

---

## TC-8 — 多会话事件隔离（回归）

**验证**：改成 per-run sink 后，多会话事件仍各归其位，不串台。

**步骤**：
1. `/session work` 发一条消息 → 等回复。
2. `/session personal` 发另一条 → 等回复。
3. `/sessions` 查看会话列表；来回 `/session work` / `/session personal` 切换。

**通过标准**：每个会话只显示自己的回复；切换后事件按当前会话过滤显示；
cron/心跳的 `Proactive` 提醒归属 `main` 视图（若配了 cron）。

## 快速冒烟（5 分钟跑一遍）

```sh
export OC_HOME=/c/dev/workspace/MyClaw/.octest
export RUST_LOG=oc=debug,oc_server=debug
cargo run --release -- serve            # 终端 A
cargo run --release                     # 终端 B（TUI）
```

TUI 里依次：
1. 发一个长回复问题 → 看是否完整（TC-1）。
2. 发 `exec sudo echo hi` → 弹审批 → 按 `y` 放行（TC-4b）→ 再来一次按 `n` 拒绝（TC-5）。
3. 触发长回复途中关掉 TUI 再重开 → `oc debug` 看会话回 idle（TC-7）。
4. 全程 `tail -f $OC_HOME/logs/oc.log.*`，确认**没有** `事件订阅滞后`。
