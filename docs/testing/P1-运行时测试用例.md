## TC-P1-1a — ask_user 提问→回答→回喂模型 ✅（最重要）

**验证**：模型调 ask_user 时，TUI 进入自由文本回答态；用户回答后，答复回喂模型，
run 继续并基于回答产出后续。

**步骤**：
1. 终端 A 启动 daemon（真实模型、带工具），终端 B 进 TUI。
2. TUI 输入一个**必须先问才能答**的请求，例如：
   > 帮我起一个项目名，但先问我这个项目是做什么的。
3. 观察 TUI 出现蓝色「提问」消息（如「这个项目是做什么的？」），并附
   `（输入回答后回车；Esc 取消）`；状态栏显示「助手提问：输入回答后回车 / Esc 取消」。
4. 在输入框键入回答（如「一个个人 AI 助手」）回车。

**通过标准**：
- 回答以「你」消息回显；状态栏恢复「已连接」后模型**基于回答**继续（给出项目名）。
- daemon 日志可见 `UserInput` 事件发出、`user.reply` 收到、工具结果含「用户回答：…」回喂。
- 全程车道不卡：提问期间状态是等待，回答后立即续跑。

**失败特征**：提问后输入框无法输入/回车无反应；或回答后模型未收到答复（答非所问）。

## TC-P1-1b — ask_user 取消（空答 / Esc）

**验证**：用户不作答时，模型收到「未作答」信号而非卡住或收到空串。

**步骤**：
1. 同 TC-P1-1a 触发提问。
2. 两种取消方式各验一次：
   - **空答**：输入框留空直接回车。
   - **Esc**：按 `Esc` 键。

**通过标准**：
- TUI 回显「（已取消回答）」，状态栏恢复「已连接」。
- 模型收到「用户未作答（已取消提问）。」，据此自行决定下一步（如用默认值或说明无法继续），
  而非空转或报错。
- 两种方式行为一致。

---

## TC-P1-1c — ask_user 等待期 abort 打断 + registry 不泄漏 🟠

**验证**：run 卡在 ask_user 等回答时，abort 能立即释放车道（P0-2 同源），
且输入 registry 不残留 entry（P0-3 同源）。

**步骤**：
1. 触发提问（同 TC-P1-1a），**不回答**。
2. `oc debug`（终端 C）确认该会话有活跃 run（phase `tool-exec`，卡在 ask_user）。
3. 触发 abort：TUI 当前在输入态可先按 `Esc` 取消提问；若要验证**真正的 abort 路径**，
   改用第二个客户端或 kill TUI（见 TC-P1-1e），核心是验证 server 侧 cancel 能解除等待。

**通过标准**：
- abort/断连后 run 立即以错误终态收尾（<2s），车道释放，`oc debug` 回 `idle`。
- 输入 registry 被 `InputGuard` RAII 清理，长期反复操作无单调增长。

> 原理：`request_input` 的 `select!` 叠 cancel + `InputGuard` drop 清理，见
> [tools_bridge.rs](../../crates/oc-server/src/tools_bridge.rs)。自动化由 `ask_user.rs` 的
> `abort_interrupts_pending_ask_user_and_cleans_registry` 断言 `<2s` 释放 + `registry.is_empty()`。

## TC-P1-1d — ask_user 阻塞 vs message 不阻塞（语义区分）

**验证**：`ask_user` 阻塞等答复，`message` 单向通知不等——两者不混淆。

**步骤**：
1. 引导模型先 `message` 通知再 `ask_user` 提问，例如：
   > 先用 message 告诉我你准备做什么，再用 ask_user 问我要不要继续。
2. 观察两条消息的行为差异。

**通过标准**：
- `message` 内容作为「工具」消息流出后 run **不停顿**、立即进入下一步（提问）。
- `ask_user` 提问后 run **停顿**等待，直到用户回答/取消才继续。

## TC-P1-1e — 断连不锁车道（ask_user 等待中关 TUI）

**验证**：ask_user 等回答期间 TUI 断开，run 感知回执通道不可达并收敛，车道不被锁。

**步骤**：
1. 触发提问（同 TC-P1-1a），**不回答**。
2. 直接关闭 TUI 进程（Ctrl-C 退出，非 `/stop`）。
3. 重开 TUI 或跑 `oc debug`。

**通过标准**：
- daemon 不崩溃；`oc debug` 显示该会话**很快**（秒级）回 `idle`（run 收敛，未占道）——
  **不是**等到空闲看门狗阈值（默认几十秒）才释放。
- 重连后能正常发消息、正常回复；输入 registry 无残留。

> **原理（2026-08-31 修复）**：ask_user/审批的等待是**静默期**——发出请求事件后卡在
> `rx.await`，期间不再 `sink.send()`，故**无法靠 send 失败探测断连**（那是 P0-1 长回复
> 路径的机制）。修复前 client 掉线后 run 只能干等到空闲看门狗兜底（真机实测约 34s，
> 期间新消息只能排队）。
> 修法两处配合：① `RunSink::closed()` 暴露下游关闭信号，`request_input`/`request_approval`
> 的 `select!` 叠这条 → 断连即 `cancel` 收敛（[tools_bridge.rs](../../crates/oc-server/src/tools_bridge.rs)）；
> ② conn 收尾改 `writer_handle.abort()` 而非无限 `await`——否则活跃 run 持有的 `out_tx`
> clone 会让写任务永不退出、`closed()` 永不触发（[conn.rs](../../crates/oc-server/src/conn.rs)）。
> 自动化：`ask_user.rs` 的 `client_disconnect_during_ask_user_converges_fast`（断言 <2s 收敛）。

## 快速冒烟（P1，3 分钟）

启动同 P0（真实模型、带工具）。TUI 里依次：
1. 发「起个项目名，但先问我做什么的」→ 出现提问 → 回答 → 看模型基于回答续跑（TC-P1-1a）。
2. 再发一次，这次按 `Esc` 取消 → 看模型收到「未作答」并妥善处理（TC-P1-1b）。
3. 触发提问后不答，关掉 TUI 重开 → `oc debug` 看会话回 idle（TC-P1-1e）。
4. 全程 `tail -f $OC_HOME/logs/oc.log.*`，确认 `UserInput`/`user.reply` 成对出现、无残留告警。

## 引导范例（让模型主动调 ask_user）

模型只在「信息不足需澄清」时才调 ask_user。以下提问易触发：
- 「帮我写个函数，但拿不准细节时先问我。」
- 「给我推荐一家餐厅——先问清我的口味和预算。」
- 「重命名这个变量，如果有歧义先问我新名字。」

若模型不调工具（直接猜答），属**模型决策**而非功能缺陷：可换更明确的引导，或在 SOUL/系统
提示里强化「信息不足时用 ask_user 澄清，不要臆测」。
